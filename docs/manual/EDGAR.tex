\begin{abstract}
\noindent
\texttt{EDGAR.jl} turns company filings into analysis-ready data in Julia. From the U.S.\ SEC's
\href{https://www.sec.gov/search-filings/edgar-application-programming-interfaces}{EDGAR} system it pulls a
filer's \emph{submission history}, the \emph{XBRL financial facts} extracted from its filings, cross-filer
\emph{frames}, and \emph{full-text search} of filing contents. The same jurisdiction-agnostic core reaches
the EU (\emph{ESEF}), the UK (\emph{Companies House} and the \emph{NSM}), Japan (\emph{EDINET}) and South
Korea (\emph{DART}); and a format-agnostic extraction axis is being extended from tagged XBRL to \emph{PDF
reports}, so a filing's facts are recovered whether it is machine-tagged or published only as a PDF.
\end{abstract}

\chapter{Introduction}
\label{sec:intro}
EDGAR (\emph{Electronic Data Gathering, Analysis, and Retrieval}) is the U.S. Securities and Exchange Commission's electronic filing system. All publicly listed companies in the United States submit their regulatory disclosures through EDGAR. Since 2009, financial statements within these filings have been tagged using XBRL (eXtensible Business Reporting Language), enabling structured, machine-readable access to financial data.

The SEC provides public access to this information through open JSON REST APIs that do not require registration or API keys. To ensure fair access, the SEC imposes a rate limit of approximately ten requests per second. The caching layer in \texttt{EDGAR.jl} (\S\ref{sec:caching}) helps ensure that usage remains well below this threshold.

\texttt{EDGAR.jl} wraps these endpoints in a lightweight, type-stable API and returns standard Julia objects such as \texttt{NamedTuple}s and \texttt{JSON3} structures. These can be directly integrated with \texttt{Tables.jl}, \texttt{TimeSeries.jl}, or database backends. The package supports three main categories of functionality:

\begin{itemize}[nosep]
  \item \textbf{Filings:} access and process SEC submissions, including listing a filer’s documents, downloading filing packages, converting filings to text, and extracting structured sections such as \emph{Financial Statements} or \emph{Management's Discussion and Analysis}.

  \item \textbf{XBRL Financial Data:} retrieve structured financial facts, including all reported data for a filer (\texttt{company\_facts}), time series for a single concept (\texttt{company\_concept}), or cross-sectional data for a concept across all filers for a given period (\texttt{xbrl\_frames}).

  \item \textbf{Full-Text and CIK Search:} query the contents of filings since 2001 using keyword search via (\texttt{filings\_by\_text}) or CIK codes via (\texttt{filings\_by\_cik}).
\end{itemize}

\medskip
\noindent Beyond these API wrappers, \texttt{EDGAR.jl} adds an interactive
extraction-to-analysis pipeline (Table~\ref{tab:at-a-glance}): \emph{pick} a statement in a
rendered filing --- or bulk-extract a whole filing with no browser --- \emph{export} it four ways,
build a queryable fact \emph{warehouse}, \emph{enrich} it from the filing's own XBRL linkbases,
and \emph{analyse} it as a stitched, cross-period statement. Every fact is traceable back to the
exact region it came from, and the extracted values are validated against the SEC's
\texttt{companyfacts} API.

\chapter{Quick Start}
\label{sec:quickstart}

\section{Searching}
\label{sec:qs-search}

Resolve a ticker to a CIK, then search the text of filings:

\begin{lstlisting}
using EDGAR
set_user_agent("Jane Doe jane@example.com")

# Ticker -> 10-digit, zero-padded CIK (exact match -> 0 or 1 row)
id = only(cik("AAPL"; by = :ticker)).cik   # "0000320193"

# Full-text search across filing contents (2001 onward), restricted to 10-K forms
rows = filings_by_text("climate risk"; forms = "10-K")   # a Tables.jl row table
for f in first(rows, 5)
    println(f.filed, "  ", f.form, "  ", f.entity)
end
\end{lstlisting}


\section{Filing Formats: Documents and iXBRL}
\label{sec:qs-reports}

\emph{Structured extraction of financial statements from inline XBRL (iXBRL) is
planned and not yet available.} The SEC tags the financial statements directly
inside each filing's primary HTML document; a future release will parse those
\texttt{<ix:\dots>} tags into tidy tables.

In the meantime you can already work with the filing \emph{documents}: list a
filer's filings, download a filing, convert it to text, and pull named sections
(see \S\ref{sec:api-filings}). For the \emph{tagged numbers} that underlie the
statements today, use the XBRL data API above (\S\ref{sec:qs-findata}) --- the
SEC has already extracted those facts for you, so you rarely need to parse the
iXBRL by hand.


\section{Financial Data}
\label{sec:qs-findata}

The three XBRL endpoints share the \texttt{us-gaap} vocabulary and return JSON:

\begin{lstlisting}
# Every XBRL fact a company has reported, in one document
facts = company_facts("320193")
gaap  = facts.facts[Symbol("us-gaap")]      # us-gaap has a hyphen: index by Symbol

# One concept over time (net income, grouped by unit)
ni = company_concept("320193", "us-gaap", "NetIncomeLoss")
println(ni.units.USD[end].val)

# The same concept across every filer for one period (a cross-section)
assets = xbrl_frames("us-gaap", "Assets", "USD", "CY2022Q4I")
println(length(assets.data), " filers reported Assets")
\end{lstlisting}

\noindent
A trailing \texttt{I} on the frame period (\texttt{"CY2022Q4I"}) denotes an
\emph{instant} (a balance-sheet point in time); drop it for a \emph{duration}
(a flow such as revenue). See the Glossary (Appendix~\ref{sec:glossary}).


\chapter{Architecture and Portability}
\label{sec:architecture}

EDGAR.jl is built around a deliberate split: a \textbf{jurisdiction-agnostic core} and a thin
\textbf{jurisdiction layer}. This applies to both subsystems --- XBRL extraction and HTML document
parsing. The XBRL core --- the regex-based extractor that resolves contexts, units
and facts from raw \texttt{<ix:nonFraction>} / \texttt{xbrli:context} / \texttt{xbrli:unit}, the
\texttt{Fact}/\texttt{Selection} model, the four export layers, the DuckDB warehouse, the browser
picker, and the linkbase \emph{parsers} --- depends on no SEC-specific assumption. It has been
validated unchanged against a non-SEC filing: the GLEIF 2024 annual report (an ESEF/IFRS report in
both inline \texttt{.xhtml} and classic \texttt{.xbrl} form) extracts identically from both
serializations, using the IFRS \texttt{ifrs-full} taxonomy, a \texttt{gleif} extension namespace,
and an LEI entity identifier --- none of which the core was written for.

What is genuinely SEC-specific is small: \emph{how} a filing is discovered and fetched, \emph{where}
its linkbases live, how its filer is \emph{identified}, the role-name \emph{vocabulary} used to
classify statements, and the SEC-only structured-data APIs. Table~\ref{tab:portability} shows where
the lines fall. SEC is the one jurisdiction implemented today; other jurisdictions (ESEF report
packages, Canada's SEDAR+) would supply only their slice of the jurisdiction column. Concretely, the
common parsing already lives in \texttt{extract\_xbrl.jl} and the SEC linkbase access in
\texttt{extract\_xbrl\_sec.jl}.

The same fault line runs through the \emph{text}-section layer (prose extraction). Here, however, the
common substrate is \emph{small}: only the HTML document parser --- the \texttt{documents/} parser
core (HTML$\rightarrow$node tree, text and table rendering) --- is jurisdiction-agnostic
and could serve an ESEF or EDINET HTML filing unchanged. Everything layered above it is
SEC-specific: the \emph{Item~N}/\emph{Part} section model has no ESEF/EDINET analog, so the section detectors
(the \texttt{documents/} TOC/heading/pattern detectors and filing-agent logic), the
\texttt{ChunkedDocument} port (\texttt{chunked\_document.jl}), \texttt{sections.jl}, the
cross-reference-index strategy (\texttt{cross\_reference.jl}), and the per-form text accessors
(\texttt{TenK}, \texttt{TwentyF}, and the 40-F AIF extractor) are all jurisdiction-specific. Unlike
XBRL --- a universal standard, where the common/specific split is roughly even --- the text-section
common part is only the HTML parser, because a filing's \emph{item} structure is a national
regulatory construct rather than a shared technical standard.

than a rewrite.

\section{Statement classification: two orthogonal axes}
\label{sec:two-axes}
\label{sec:classification-layers}

Deciding which financial statement a fact belongs to (\texttt{statement\_map}, \S\ref{sec:export-layers})
is the part most exposed to the messy diversity of real filings, so it is worth being explicit about
how that knowledge is layered. The robust approach --- a multi-signal scorer adapted from
\href{https://github.com/dgunning/edgartools}{edgartools} (MIT; see Acknowledgements) --- factors
along the \emph{taxonomy}, \emph{not} the jurisdiction. There are three layers
(Table~\ref{tab:classify-layers}).

\begin{table}[h]
\centering
\caption{The three layers of statement-classification knowledge.}
\label{tab:classify-layers}
\small
\begin{tabular}{@{}p{0.17\textwidth}p{0.60\textwidth}p{0.16\textwidth}@{}}
\toprule
\textbf{Layer} & \textbf{What it is} & \textbf{Shared by} \\
\midrule
\textbf{Engine logic} (common) & The cascade + scoring + validation \emph{meta-rules}: prefer a complete statement over a fragment, validate that essential concepts are present, reject the wrong type, penalize parentheticals, and combined-statement aliasing. Plus the structural semantics --- a balance sheet \emph{is} Assets + Liabilities + Equity; an income statement runs revenue $\to$ profit. & All taxonomies \& jurisdictions \\
\textbf{Taxonomy vocabulary} (per-taxonomy, often shared) & The concept anchors, concept patterns and role-name patterns. \texttt{ifrs-full} (profit-or-loss, financial position, changes in equity) is reused by ESEF, SEDAR+ (IFRS), Companies House (IFRS), DART (K-IFRS), MOPS (TW-IFRS) and EDINET (IFRS filers). \texttt{us-gaap} (tax-disclosure penalties, comprehensive-income variants, roll-forwards) is SEC. National GAAPs (JP \texttt{jpcrp}/\texttt{jppfs}, UK FRS~101/102, KR) are one regime each. & the taxonomy's users \\
\textbf{Jurisdiction adapter} (per-jurisdiction) & Discovery/fetch, linkbase location, identity (CIK / LEI / \ldots), the filing-package conventions (SEC's \texttt{FilingSummary.xml} + R-files; ESEF zip; EDINET/DART APIs), and which taxonomies the regime uses. & one jurisdiction each \\
\bottomrule
\end{tabular}
\end{table}

\noindent The edgartools scorer encodes roughly two dozen empirically-tuned, issue-driven rules
(each a real filing that broke a naive classifier, then a fix). Of those, about \emph{45\%} is common
engine logic, \emph{30\%} \texttt{us-gaap} data, and \emph{20\%} \texttt{ifrs-full} data --- and that
IFRS slice is reused across the jurisdictions above. Almost nothing in the engine is SEC-specific, so
adopting it front-loads both the engine \emph{and} the IFRS vocabulary: adding ESEF / Companies House
/ DART / MOPS / EDINET becomes mostly adapters plus reuse, with a new national-GAAP vocabulary only
where a regime actually uses one (chiefly Japan and the UK).

This refines the portability picture above into \textbf{two orthogonal axes}: a \emph{jurisdiction}
axis (\texttt{SEC <: Jurisdiction}, \ldots) handling fetch and identity, and a separate
\emph{taxonomy} axis (\texttt{us-gaap} / \texttt{ifrs-full} / \ldots\ vocabularies, auto-selected from
the concept prefixes a filing actually uses) handling classification. EDGAR.jl ships the
classification \emph{registry} today; the full per-request scoring cascade is a planned, test-anchored
port of the edgartools resolver. (This is a design direction and may change in detail.)


\section{Extraction \textemdash{} from filings to facts}
\label{sys:extraction}

A fetched \texttt{Filing} is only bytes plus a \texttt{kind}. An \textbf{extractor} turns it into the
\texttt{FactRow} row table that the rest of the toolkit consumes. \texttt{EDGAR.jl} has more than one
extractor, selected automatically by \texttt{facts(f)} from the filing's format. Whatever the source,
the output is the \emph{same} row table --- so classification, \texttt{select\_statement}, the
CSV/DuckDB exports and the validation oracles (\S\ref{sec:validation}) all work unchanged.

\subsection{Architecture: the format/extraction axis}

The portability picture (\S\ref{sec:two-axes}) has two axes --- a \emph{jurisdiction} axis (fetch and
identity) and a \emph{taxonomy} axis (the concept vocabulary). Extraction is a \textbf{third,
orthogonal axis: \emph{format}} --- \emph{how} facts are recovered from the bytes. \texttt{Filing.kind}
names it (\texttt{:ixbrl}, \texttt{:xbrl}, \texttt{:pdf}), and \texttt{facts(f)} dispatches on it:

\begin{itemize}
  \item \texttt{:ixbrl} / \texttt{:xbrl} \(\rightarrow\) the \textbf{XBRL extractor} (reads inline or
    classic XBRL, resolving contexts and units). This is the path every structured filing has used so far.
  \item \texttt{:pdf} \(\rightarrow\) the \textbf{PDF extractor}, described in Chapter~\ref{ch:pdf}
    (\emph{PDF Reports}).
\end{itemize}

\noindent The key invariant: \textbf{both emit the same \texttt{FactRow}}. So the XBRL parser is
\emph{one} extractor on this axis, not the universal core --- a point the Companies House and German
cases force, where a large share of filings are PDF, not XBRL. (The PDF extractor itself --- the main
document-AI approach and its deterministic fallback --- has its own chapter, \emph{PDF Reports},
Chapter~\ref{ch:pdf}.)

\subsection{Where it plugs into the workflow}

Extraction is one step in the same pipeline every system follows:

\begin{center}
\texttt{company\_search} \(\rightarrow\) \texttt{discover} \(\rightarrow\) \texttt{fetch\_filing}
\(\rightarrow\) \textbf{\texttt{facts(f)}} \(\rightarrow\) \texttt{select\_statement} / export / validate
\end{center}

\noindent The extractor \emph{is} the \texttt{facts(f)} step, and it is identical for every jurisdiction
--- SEC, ESEF, Companies House, the NSM. For XBRL filings \texttt{facts(f)} ``just works''. For PDF the
working entry today is \textbf{\texttt{extract\_pdf(path)}} on a born-digital PDF on disk; calling
\texttt{facts(f)} on a \texttt{:pdf} \texttt{Filing} currently needs the PDF bytes, which the fetch path
does not yet retain --- so download the document, then \texttt{extract\_pdf}. (The deterministic fallback covers born-digital
financial statements today; scanned and exotic layouts await the document-AI main path --- see
Chapter~\ref{ch:pdf}.)

\subsection{Workflow examples}

The extraction call is the same shape across systems; only discovery differs.

\paragraph{SEC (inline XBRL).}
\begin{lstlisting}

set_user_agent("Your Name you@example.com")

\chapter{PDF and HTML reports}
\label{ch:pdf}

Many regulatory filings are PDF, not XBRL --- at Companies House the format is unpredictable and much of
the registrar is PDF, and Germany has no openly retrievable XBRL at all. The PDF extractor turns such a
report into the \emph{same} \texttt{FactRow} row table the XBRL path produces (and, in time, the document
family --- sections, descriptive tables and figures), so classification, \texttt{select\_statement}, the
CSV/DuckDB exports and the validation oracles all work unchanged.

\paragraph{The concept problem.} An XBRL fact carries a taxonomy \emph{concept}
(\texttt{us-gaap:Assets}); a PDF fact carries only a line-item \emph{label} (``Total assets'',
``Bilanzsumme''). So for PDF the \texttt{standard\_concept} (the cross-company standardiser) is the real
bridge, and classification keys off the label rather than a concept prefix. The fact's
\texttt{source\_selector} carries a CSS selector for HTML filings and, for PDF, the source
\texttt{(page, bbox)} --- coordinate provenance that lets an editor back-link a number to its source pixel.

\section{Two paths: document AI (main) and a deterministic fallback}

PDF is the hard case: a born-digital PDF has no rows or columns, just positioned text; scanned PDFs have
no text layer at all; and layouts vary by issuer and language. \texttt{EDGAR.jl} therefore uses a
\textbf{document-AI engine as the main approach}, and falls back to a \textbf{light deterministic path}
when that engine is not installed:

\begin{itemize}
  \item[\textbf{Main}] \textbf{--- document AI (Docling or MinerU).} A document-structuring engine turns
    the \emph{whole} PDF --- including scanned pages and non-Latin scripts --- into one Structured
    Document, from which both the financial facts \emph{and} the narrative, descriptive tables and figures
    are derived. This is the primary path; it is a heavier install (a Python stack, optionally a GPU) and
    so is opt-in.
  \item[\textbf{Fallback}] \textbf{--- deterministic pdf.js.} When neither Docling nor MinerU is
    installed, a light Node\,+\,pdf.js path reconstructs the financial \emph{statements} geometrically ---
    rows by vertical position, columns by the numeric right-edge bands --- and emits coordinate-anchored
    facts. No Python, no GPU, no model downloads; statements-only. A graceful floor, not the main path.
\end{itemize}

\noindent Both paths emit the same \texttt{FactRow}, so everything downstream is identical regardless of
which ran. The fallback's number semantics (parentheses\,=\,negative, decimal-comma, scale footers) are
written in Julia and are reused to discipline the main path's output. \emph{Status:} today the
deterministic fallback is the implemented path (\texttt{extract\_pdf}, \S\ref{sec:pdf-fallback}); the
document-AI main path is in development.

\section{The main approach: Docling versus MinerU}
\label{sec:pdf-docai}

Both engines convert a PDF into one Structured Document from which every derivation is taken; they differ
in weight and in how they handle OCR and language (Table~\ref{tab:pdf-docai}). \texttt{EDGAR.jl} carries
\emph{both}, so they can be compared on real filings and one selected later --- both work well in practice
(Docling needs an OCR pass only for broken-text-layer cases such as Japanese EDINET; MinerU needs the
document language set correctly). The stack is Python (installed via
\texttt{PythonCall}\,+\,\texttt{CondaPkg}) and is therefore available only in the stand-alone package, not
in the editor host.

\paragraph{OCR: a plugin in Docling, bundled in MinerU.} The two engines treat OCR differently, and this
is what drives the install:
\begin{itemize}
  \item \textbf{Docling --- OCR is a plugin.} It reads the text layer first and invokes OCR only when text
    is missing, so born-digital filings need \emph{no} OCR engine at all. When OCR is needed you choose an
    engine --- EasyOCR, \textbf{RapidOCR}, Tesseract, or (macOS) the Vision framework. \texttt{EDGAR.jl}
    favours \textbf{RapidOCR}: it is ONNX-based, installs with \texttt{pip} alone (\emph{no} external
    system binary, unlike Tesseract), and is light and fast on CPU. In practice only broken-text-layer
    filings (e.g.\ Japanese EDINET) trigger it.
  \item \textbf{MinerU --- OCR is bundled.} OCR (PaddleOCR) is always part of the pipeline, so there is
    nothing to choose --- but the classic \texttt{pipeline} backend needs the document \emph{language}
    set correctly, or non-default scripts can be dropped \emph{silently}; its newer VLM backend is
    multilingual without a hint but requires a GPU. Because \texttt{EDGAR.jl} knows each filing's
    \texttt{FilingSystem} it largely knows the language already, so setting it is cheap.
\end{itemize}

\section{Statement classification and the PDF outline}
\label{sec:pdf-classification}

Once a report is in the repository, each table is tagged with a \emph{class}: \texttt{kind}
(\texttt{statement} vs \texttt{descriptive}) and, for statements, a \texttt{statement\_type}. The starter
taxonomy is the four core statements --- \texttt{balance\_sheet}, \texttt{income\_statement},
\texttt{cash\_flow}, \texttt{equity\_changes} --- but the registry is \textbf{open}: other periodic
quantitative tables (e.g.\ a fund's portfolio holdings) are added with \texttt{register\_table\_class!}
and need no schema change. Classification is multi-language: each class carries heading patterns in
English, French, German, Spanish, Italian and CJK. Run it with \texttt{classify\_tables!(db)}.

\paragraph{The problem: the heading is not always where you expect.} A table is classified by matching a
\emph{heading} against the patterns --- but which text is the heading? The obvious choice, the table's
enclosing section title, is fragile: some issuers print a brand band (e.g.\ ``TotalEnergies'') at the top
of every statement page, and the parser mistakes \emph{that} for the section heading, masking the real
title (``Bilan consolidé''). Others vary the wording (\texttt{Bilan} instead of \texttt{État de la
situation financière}; \texttt{Variation des capitaux propres} without the \texttt{État de} prefix), which
defeats over-literal patterns.

\paragraph{The strategy: layered heading sources, with the PDF outline as the authority.} The classifier
considers, in order, several candidate headings for each table:
\begin{enumerate}
  \item the table's own \textbf{caption};
  \item its \textbf{enclosing section title};
  \item the nearest preceding \textbf{heading-like text block on the same page} (recovers a title the
    brand band masked);
  \item the entry of the \textbf{PDF outline (bookmarks)} that covers the table's page.
\end{enumerate}
The fourth is the robust one. A PDF's outline is an \textbf{authoritative} table of contents --- exact
titles with page ranges, immune to page-header noise --- so mapping a table's page to its covering outline
entry recovers the true heading even when the on-page text is unreliable. \texttt{EDGAR.jl} captures the
outline at ingestion into the \texttt{toc} table (it also serves navigation), and the classifier maps each
table's page to the nearest preceding \texttt{toc} entry.

For example, TotalEnergies' consolidated statements carry the brand ``TotalEnergies'' as their on-page
heading, so section-title matching tags nothing; but the outline entries
(\texttt{8.4~Bilan~consolidé}~$\rightarrow$~p423, \texttt{8.2~Compte~de~résultat~consolidé}~$\rightarrow$~p421,
\dots) classify every statement correctly --- including \emph{both} halves (ACTIF and PASSIF) of the
two-part French \emph{Bilan}. Where a PDF has no outline, the earlier sources still apply.

\section{The deterministic fallback}
\label{sec:pdf-fallback}

When the document-AI stack is absent, the fallback runs: a \textbf{single Node/TypeScript toolchain} ---
no Python/Conda, no JVM, no GPL/AGPL. The parser is \texttt{pdfjs-dist} used \emph{directly}: Mozilla's
upstream pdf.js (Apache-2.0), pinned to a version we choose. In a bake-off it tied the popular wrappers
(\texttt{pdf.js-extract}, \texttt{pdfreader}) on accuracy while being faster, leaner on dependencies, and
on the best-maintained parser (the wrappers bundle older or \emph{forked} copies). It is also native to
the editor host (a TypeScript VS Code fork), where the same \texttt{pdf.js} can render, extract \emph{and}
supply the coordinates that link a fact to its source. Using it needs Node and the pinned
\texttt{pdfjs-dist} (\texttt{npm install} in \texttt{src/extractors/pdf/}). It is the entry point that
works today --- \texttt{extract\_pdf(path)} on a born-digital PDF returns a \texttt{Vector\{FactRow\}},
exactly like \texttt{facts(f)}:

\begin{lstlisting}
rows = extract_pdf("annual_report.pdf"; page = 133)      # a Vector{FactRow}, like facts(f)
select_statement(rows, "BalanceSheet")                   # every fact coordinate-anchored
\end{lstlisting}

\section{HTML input (e.g.\ SEC N-CSR)}
\label{sec:html-input}

The pipeline is not PDF-only. \texttt{structured\_document} also accepts \textbf{HTML} (\texttt{.htm} /
\texttt{.html}) --- useful for filings published as HTML rather than PDF, such as a US fund's SEC
\emph{N-CSR}. Detection is by extension: an HTML file is routed through Docling's HTML pipeline (the
\texttt{pages} and \texttt{ocr} options do not apply), and from there it is the \emph{same} flow ---
\texttt{StructuredDocument} $\rightarrow$ \texttt{persist\_document} / \texttt{to\_repository}
$\rightarrow$ \texttt{classify\_tables!} --- so nothing downstream changes.

\begin{lstlisting}
julia> using EDGAR, PythonCall, DuckDB
julia> sd = structured_document("US-FidelityContrafundNCSR.htm";
                                jurisdiction = "US", language = "en", report_type = "N-CSR")
julia> to_repository(sd)
\end{lstlisting}

\paragraph{Caveats versus PDF.} HTML carries less layout signal, so two heading sources are weaker or
absent:
\begin{itemize}
  \item \textbf{No page coordinates.} HTML has no pages, so \texttt{(page, bbox)} provenance comes through
    empty (page~0). The pixel back-link is therefore unavailable for HTML-sourced facts.
  \item \textbf{No PDF outline, and often no sections.} Docling's HTML backend may emit \emph{no} section
    headers (headings arrive as ordinary text blocks) and there is no bookmark outline. Classification
    (\S\ref{sec:pdf-classification}) then falls back to the table caption and the nearest preceding
    heading text block, rather than the section title / outline.
  \item \textbf{SEC SGML wrapper tolerated.} A raw SEC submission document begins with an SGML
    \texttt{<DOCUMENT>} wrapper around the HTML; Docling parses it regardless.
\end{itemize}

\noindent Validated on a Fidelity \emph{Contrafund} N-CSR: Docling recovered \textasciitilde1{,}690 text
blocks, 194 tables and 12 figures into the repository --- the same contracts as a PDF, minus page/outline
provenance.

\chapter{Common API}
\label{sec:api}

CIKs are the SEC Central Index Key, zero-padded to 10 digits (Apple $\to$
\texttt{0000320193}). Any \texttt{cik} argument accepts an integer or a string, with
or without leading zeros (\texttt{320193}, \texttt{"320193"} and \texttt{"0000320193"}
are equivalent); functions normalize to the 10-digit form. Every data call goes
through the cached, User-Agent-aware request layer (\S\ref{sec:ua}).

\subsection{\texttt{cik}}

\paragraph{Signatures}
\begin{description}
  \item[\sig{cik()}] 
  \item[\sig{cik(entity; by = :name | :ticker | :any)}] 
\end{description}



\paragraph{Selection Criteria}
\begin{itemize}
  \item \texttt{cik()} returns all entities with an associated CIK code in the EDGAR dataset.
  \item \texttt{cik(entity\_query; by = :name | :ticker | :any)} selects entities by matching the input string against the company name, ticker, or both, depending on the \texttt{by} argument.
\end{itemize}
\paragraph{Keyword Arguments}
\begin{description}[nosep]

  \item[\quad - \texttt{by}]~
  \begin{description}[nosep]
    \item[\quad \texttt{:any}] (default) matches rows where \texttt{entity\_query} appears either as a substring in the entity name (case-insensitive) or as an exact ticker match. For example, \texttt{"IBM"} matches the ticker IBM, while \texttt{"apple"} matches company names containing that string. Each row is tested once, so a row matching both appears only once.
    \item[\quad \texttt{:name}] returns rows where the entity name contains \texttt{entity\_query} (case-insensitive substring match).
    \item[\quad \texttt{:ticker}] returns at most one row matching the exact ticker (case-insensitive).
  \end{description}
\end{description}

\paragraph{Return Value} Both forms always return a \texttt{Tables.jl} \emph{row table}, with fields 
\begin{itemize}
  \item \texttt{entity}
  \item \texttt{ticker}
  \item \texttt{cik}
\end{itemize}
with one record per ticker.

The return type is consistent across all modes, ensuring type stability. The result behaves as a standard Tables.jl-compatible object and can be directly consumed by downstream tools such as \texttt{DataFrames.jl}, \texttt{TimeSeries.jl}, \texttt{CSV.jl}, \texttt{XLSX.jl}, \texttt{Parquet.jl}, or database interfaces such as \texttt{SQLite.jl}.

A query may yield several rows, because (a) one company can have multiple tickers
(e.g. share classes \texttt{GOOGL}/\texttt{GOOG}), and (b) several companies may match
the query in their name.

\subsection{\texttt{full\_text\_search}}

\paragraph{Signature}
\begin{description}
  \item[\sig{full\_text\_search(text; exact=true, forms=nothing, startdate=nothing, enddate=nothing, from=0)}]
\end{description}

\noindent \texttt{full\_text\_search} is the SEC's own name for this endpoint (EFTS); it is also exported under the alias \texttt{filings\_by\_text}, and pairs with \texttt{filings\_by\_cik}. The function
\texttt{full\_text\_search} discovers \textit{filings} by their content (e.g. "which filings mention 'supply chain disruption'?"). Search the full text of SEC filings, everything filed from 2001 onward, for some \texttt{text} through the EDGAR full-text search (EFTS) API. 

\paragraph{Keyword Arguments}
\begin{description}[nosep]
  \item[\quad - \texttt{exact}]
  \item[\quad - \texttt{forms}] may be a single string (\texttt{"10-K"})\footnote{Form 10-K is a detailed annual filing submitted by public companies to the SEC. It provides a comprehensive overview of the company's business activities, financial health, and key risks. The filing includes audited financial statements, management's discussion of financial results, information about the company's operations and strategy, disclosures on legal and regulatory issues, and an assessment of risk factors that could affect future performance.} or a collection; 
  \item[\quad - \texttt{startdate}] is a \texttt{"YYYY-MM-DD"} format string
  \item[\quad - \texttt{enddate}] is a \texttt{"YYYY-MM-DD"} format string 
  \item[\quad - \texttt{from}] is the 0-based offset used to page (EFTS returns a fixed page of 100 results per request). 
\end{description}
By default the (\texttt{text}) is matched \textbf{exactly}, so
\texttt{"supply chain disruption"} finds only filings with those three words adjacent;
pass \texttt{exact = false} to match the words loosely instead. Results come back
ranked by relevance, not by date.

\paragraph{Return Values.} The method \texttt{full\_text\_search()} returns a \texttt{Tables.jl} \emph{row table}, a row per matching filing for the current page (up to 100). There is no total-match count; to page, advance (\texttt{from}) in steps of 100 until you get fewer than 100 rows. The returned columns are described in Table~\ref{tab:full_text_search}.

\subsection{\texttt{filings\_by\_cik}}

\paragraph{Signature}
\begin{center}
\textbf{\sig{filings\_by\_cik(cik; forms = nothing, startdate = nothing, enddate = nothing, from = 0)}}
\end{center}


\noindent List a single filer's filings (2001 onward) through the same EFTS
endpoint, but keyed by its \texttt{cik} (an integer or string, padded or not) using
EDGAR's \emph{entity} filter --- the web form's company/CIK field. This is a true
``filed by this filer'' query, unlike full-text searching for the CIK as document
text, which also matches filings that merely \emph{mention} it (e.g.\ a fund listing
the company among its holdings). 

\paragraph{Keyword Arguments}
\begin{description}[nosep]
  \item[\quad - \texttt{forms}] behaves as for \texttt{full\_text\_search}

\subsection{The \texttt{Filing} Type}
\label{sec:filing-type}

\noindent A \texttt{Filing} is an immutable value representing a filing document in
memory. It is defined as a simple \texttt{struct} with six fields:

\begin{lstlisting}
struct Filing
    cik::String         # 10-digit, zero-padded Central Index Key
    accession::String   # dashed accession number
    document::String    # the primary document's filename
    url::String         # the EDGAR Archives URL it was fetched from
    kind::Symbol        # :ixbrl, :xbrl, or :html
    content::String     # the raw document text (HTML or XML)
end
\end{lstlisting}

\noindent In normal use, \texttt{Filing} instances are created by
\texttt{fetch\_filing}, which populates all fields from the SEC submissions data and
the retrieved document. Because \texttt{Filing} is a plain \texttt{struct}, the
default constructor
\texttt{Filing(cik, accession, document, url, kind, content)} is also available,
which can be useful in tests or when reconstructing a filing from previously saved
content and metadata.

Fields are accessed directly using dot notation. For example,
\texttt{f.content} contains the document text processed by the extraction helpers, \texttt{f.kind} distinguishes between iXBRL, XBRL, and HTML filings, and \texttt{f.url} records the document's source. A \texttt{Filing} also displays as a
compact one-line summary in the REPL and renders inline as HTML in notebook front-ends (\S\ref{sec:display-filing}).


\subsection{Displaying a \texttt{Filing}}
\label{sec:display-filing}

\paragraph{Web Browser}
The primary way to inspect a \texttt{Filing} is in a web browser via
\texttt{open\_filing}. The function writes the filing to a temporary HTML file,
downloads any referenced assets (such as images), rewrites the corresponding URLs
to point at the local copies, and then opens the result in the system's default
browser.

\begin{lstlisting}
julia> f = fetch_filing(320193, "0000320193-25-000079")
julia> open_filing(f)
\end{lstlisting}

\noindent For \texttt{:ixbrl} and \texttt{:html} filings, the browser displays the
document exactly as a normal web page. Since iXBRL is itself an HTML document with
embedded XBRL markup, the filing renders as the familiar report submitted to the
SEC, including tables, styling, and images.

A \texttt{:xbrl} filing is different: it contains XML rather than HTML and
therefore has no visual presentation of its own. In that case,
\texttt{open\_filing} wraps the XML in a minimal HTML page and displays it as escaped source code, allowing the underlying instance document to be inspected in the
browser.

\paragraph{Notebook} Besides opening a filing in a browser, a \texttt{Filing} can render
\emph{inline} in any rich display front-end, such as Jupyter or Pluto notebooks,
via its \texttt{text/html} \texttt{show} method. There is nothing to call explicitly:
when a \texttt{Filing} is the last expression in a cell, the front-end requests its
HTML representation and renders the filing directly in the output area.

\begin{lstlisting}
julia> f = fetch_filing(320193, "0000320193-25-000079")
julia> f          # a notebook renders the filing itself, inline
\end{lstlisting}

\noindent Notebooks render the HTML in-page, where relative image references cannot
be resolved against files on disk. To ensure that figures still appear, the
\texttt{show} method replaces each referenced image with a base64-encoded
\texttt{data:} URI — the in-memory analogue of what \texttt{download\_assets} does on
disk — making the rendered filing completely self-contained.

\paragraph{Terminal REPL}
In a plain terminal REPL there is no HTML renderer, so evaluating \texttt{f} displays a compact summary such as
\texttt{Filing(:ixbrl, “aapl-20250927.htm”, 1520208 bytes)}.
Use \texttt{open\_filing} to view the filing in a web browser instead.

\noindent Note that \texttt{:xbrl} filings contain XML rather than HTML. Because there is no visual document to render, they are displayed as escaped source within a \texttt{<pre>} block. Only \texttt{:ixbrl} and \texttt{:html} filings render as formatted documents.
\paragraph{HTML as a String}
To obtain the rendered markup as a \texttt{String} (for embedding or
post-processing), or to trigger rendering explicitly when a \texttt{Filing} is not
the final expression in a function, loop, or notebook cell, use Julia's standard
display API,

\begin{lstlisting}
julia> html = repr("text/html", f)        # the rendered HTML as a String
julia> display(f)                         # render to the active display on demand
\end{lstlisting}

\subsection{\texttt{fetch\_filing}}

\paragraph{Signature}
\begin{center}
\textbf{\sig{fetch\_filing(cik, accession; kind = (:auto) | :ixbr | :xbr | :html)}}
\end{center}

\noindent Fetch a single filing's document from the EDGAR \texttt{Archives} into
memory (no disk write). The fetch goes through \texttt{fetch\_url}, so it is
cached and uses the configured User-Agent. 

\paragraph{Keyword Arguments}
\begin{description}[nosep]
  \item[\quad - \texttt{cik}]
  \item[\quad - \texttt{accession}]
  \item[\quad - \texttt{kind}]~
  \begin{description}[nosep]
    \item[\quad \texttt{:auto}] (default) takes the iXBRL primary document when the filing has one (\texttt{isInlineXBRL}), else the classic XBRL instance (\texttt{isXBRL}), otherwise the plain primary HTML.
    \item[\quad \texttt{:ixbrl}] force the primary document
    \item[\quad \texttt{:xbrl}] force the XBRL instance (located via the filing's \texttt{index.json})
    \item[\quad \texttt{:html}] force the primary document
  \end{description}
\end{description}

\paragraph{Return Value.}
A \texttt{Filing} (\S\ref{sec:filing-type}), whose fields are
\begin{itemize}
  \item \texttt{cik}
  \item \texttt{accession}
  \item \texttt{document}
  \item \texttt{url}
  \item \texttt{kind}
  \item \texttt{content} --- the raw document text
\end{itemize}


\paragraph{Julia Example:} Fetch one filing using its accession number and show the primary document's name and format. 

\begin{lstlisting}
julia> f = fetch_filing(320193, "0000320193-25-000079")
# Output:
Filing(:ixbrl, "aapl-20250927.htm", 1520208 bytes)

julia> f.kind, f.document, f.url
# Output:
(:ixbrl, "aapl-20250927.htm", "https://www.sec.gov/Archives/edgar/data/320193/000032019325000079/aapl-20250927.htm")
\end{lstlisting}


\subsection{\texttt{open\_filing}}

\begin{center}
\textbf{\sig{open\_filing(f::Filing; assets = true)}}
\end{center}
\begin{center}
\textbf{\sig{open\_filing(cik, accession; kind = :auto, assets = true)}}
\end{center}
\begin{center}
\textbf{\sig{open\_filing(path::AbstractString)}}
\end{center}



\noindent View a fetched \texttt{Filing} in your default browser, returning the path
opened. A browser can only open a file or URL --- never an in-memory string --- so
this writes \texttt{f} to a fresh \emph{temporary} directory (under the filename
\texttt{f.document}, so the extension and tab title are right) and opens it. It is a
throwaway view; use \texttt{save\_filing} to keep a copy. For programmatic use no file
is needed at all. Methods such as \texttt{extract\_section} work straight off
\texttt{f.content}.

Filing's images are stored as separate files \emph{beside} the document in the
EDGAR Archives, and \texttt{fetch\_filing} downloads only the primary document, so the
HTML's relative \texttt{<img>} references would otherwise resolve to nothing and the
figures appear blank. With \texttt{assets = true} (the default) the referenced images and any CSS/JS are fetched into the same temporary directory via
\texttt{download\_assets} so the page renders complete; pass \texttt{assets = false} to
open just the HTML (faster, no extra requests). The temporary directory --- the
document and its images together --- is registered for automatic cleanup when the
Julia process exits, so nothing lingers on disk between sessions.

\begin{lstlisting}
julia> f = fetch_filing(320193, "0000320193-25-000079")
# Output:
Filing(:ixbrl, "aapl-20250927.htm", 1520208 bytes)

julia> open_filing(f)          # renders the 10-K, with its images, in your browser
\end{lstlisting}

\paragraph{Fetch and Open} For the common case where the filing is only being viewed, the convenience method
\texttt{open\_filing(cik, accession; kind = :auto, assets = true)} combines \texttt{fetch\_filing} and \texttt{open\_filing} into a single call, fetching the
filing and opening it immediately in the browser without requiring an intermediate
\texttt{Filing} object:

\begin{lstlisting}
julia> open_filing(320193, "0000320193-25-000079")   # fetch and view in one step
\end{lstlisting}

\paragraph{Reopen from Disk} A third method, \texttt{open\_filing(path::AbstractString)},
opens a filing that is \emph{already saved on disk} --- the on-disk counterpart of the
in-memory \texttt{Filing} method. It is the natural partner of \texttt{save\_filing}
(which returns the path it wrote) and works for any saved HTML page, including an
extracted section such as a balance sheet (still part of the filing). The path must
exist; an \texttt{http(s)://} URL is passed through to the browser as-is.

\begin{lstlisting}
julia> path = save_filing(f; destdir = "filings")
julia> open_filing(path)          # reload from disk and view in the browser
\end{lstlisting}


\subsection{\texttt{extract\_section}}

\begin{center}
\textbf{\sig{extract\_section(html, names; base\_path = nothing)}}
\end{center}


\noindent Pull named sections from filing HTML/text by heuristic,
case-insensitive matching --- e.g.\ \texttt{"Item 7"} or
\texttt{"Management's Discussion"}. Returns a \texttt{Dict} mapping each requested name
to its extracted text (the full section, up to where the next section begins).

\subsection{\texttt{find\_paragraphs}}

\begin{center}
\textbf{\sig{find\_paragraphs(f::Filing, query; ignorecase = true) -> Vector\{NamedTuple\{index, paragraph\}\}}}
\end{center}

\noindent Search \emph{within} one already-fetched filing for the paragraphs whose text contains
\texttt{query} --- a \textbf{literal substring} match --- returning each hit paired with its
\texttt{index} (the 1-based position among \emph{all} the document's paragraphs), or an empty vector if
the phrase never occurs. This is distinct from \texttt{filings\_by\_text}, which searches \emph{across}
SEC filings to decide \emph{which} to fetch: \texttt{find\_paragraphs} searches the prose of a
\emph{single} document, and is \textbf{jurisdiction-agnostic} --- it works on a SEC iXBRL filing or an
ESEF iXHTML report (\S\ref{sys:esef}) alike, because it operates on the filing already in memory.

\noindent The markup is reduced to plain-text paragraphs (split at block-level HTML boundaries, inline
tags stripped, whitespace collapsed), so the match ignores tags and runs of whitespace. The returned
\texttt{index} locates each hit and lets you jump back to it (and its neighbours); the result is a
Tables.jl row table, so it renders with \texttt{PrettyTables}, filters, and converts to a
\texttt{DataFrame}. Pass \texttt{ignorecase = false} for an exact-case match.

\begin{lstlisting}
f = fetch_filing(320193, "0000320193-23-000106")
hits = find_paragraphs(f, "climate-related risks")  # [(index=312, paragraph="..."), ...] or []
EDGAR._paragraphs(f.content)[hits[1].index]         # jump back to the located paragraph
\end{lstlisting}

\paragraph{Jumping to a match.} The \texttt{index} is a \emph{stable locator} into the document's
paragraph sequence, not just a row label. Today it lets you \textbf{jump} straight back to a hit ---
re-split the filing with \texttt{EDGAR.\_paragraphs(f.content)} and index into it to re-read the
paragraph, or take a window around \texttt{index} for surrounding context --- without re-scanning the
text. Because the index is computed over \emph{all} the document's paragraphs (not just the matches),
it also tells you roughly where in the filing the hit sits.

\emph{Planned.} A convenience built on this locator will open the \emph{rendered} filing in the
browser (as \texttt{open\_filing} does) and \textbf{scroll directly to the matched paragraph},
highlighting it, so a search result can be read in its original visual context --- the same
``pick / locate'' idea as the interactive picker, but driven by a text query. The \texttt{index}
returned now is exactly the handle that feature will consume; it is not yet implemented.

\subsection{\texttt{sections}}

\begin{center}
\textbf{\sig{sections(f::Filing; form = "10-K") -> Vector\{@NamedTuple\{item, title, text\}\}}}
\end{center}

\noindent Segment a filing into its \emph{items} (\texttt{"Item 1"}, \texttt{"Item 1A"}, \ldots), in
document order. Where \texttt{extract\_section} matches one section name at a time and can latch onto a
cross-reference (``see Item 1A of this report\ldots''), \texttt{sections} is a faithful, \emph{form-agnostic}
port of edgartools' \texttt{ChunkedDocument}: the document is split into text blocks, blocks are grouped
into chunks (a new chunk begins at each \texttt{Item}/\texttt{Part}/heading block, with tables as their own
chunk), each chunk's leading \texttt{Item N} line sets its item, the table of contents is dropped by item
density, the item label is forward-filled down the chunks, and the signature block truncates the tail.
Header versus body text is decided purely by word case and length, so the \emph{same} logic serves 10-K,
10-Q, 20-F, 8-K and other item-structured forms with no per-form catalogue (\texttt{form} is accepted only
for symmetry). Filings that carry no in-body \texttt{Item N} headers but a \emph{FORM 10-K Cross-Reference
Index} (e.g.\ GE, Henry Schein) are handled by a second strategy that maps items to page ranges and slices
content between page breaks. Validated at character-level parity with edgartools across a diverse set of
10-Ks.

\paragraph{Supported forms.} Item-level section extraction is available only for the \emph{item-structured}
report forms, and each has been validated at character-level parity against edgartools' \texttt{obj()[item]}:
\textbf{10-K}, \textbf{10-K/A}, \textbf{10-Q}, \textbf{8-K}, \textbf{20-F}, and \textbf{40-F}. The two annual
reports also have dedicated faithful accessors that mirror edgartools --- \texttt{TwentyF}/\texttt{tf\_section}
(20-F) and \texttt{TenK}/\texttt{tk\_section} (10-K and 10-K/A); 40-F annual reports are segmented from their
Annual Information Form exhibit. Other forms --- for example \texttt{S-1}, \texttt{S-4}, \texttt{N-CSR},
\texttt{DEF 14A} and \texttt{6-K} --- are \emph{not} segmented into named items: \texttt{sections} returns an
empty vector for them, exactly as edgartools does (its \texttt{Document.sections} is likewise empty for these
forms). Such filings can still be fetched, converted to text (\texttt{markdown}), searched
(\texttt{filings\_by\_text}), and mined for XBRL facts (\texttt{facts}); in edgartools they are served by
\emph{form-specific structured-data} parsers (e.g.\ \texttt{ProxyStatement} for DEF 14A,
\texttt{FundShareholderReport} for N-CSR, \texttt{RegistrationS1} for S-1), which \texttt{EDGAR.jl} does not
currently replicate.

\subsection{\texttt{save\_filing}}

\begin{center}
\textbf{\sig{save\_filing(f::Filing; destdir = ".", assets = true)}}
\end{center}
\noindent Write a fetched \texttt{Filing} verbatim to \texttt{destdir/f.document}, creating \texttt{destdir} if needed, and return the path. With
\texttt{assets = true} (the default) the filing's images and any CSS/JS are also
downloaded into \texttt{destdir} via \texttt{download\_assets}, so the saved copy renders
self-contained. Pass \texttt{assets = false} to write only the document. 


\subsection{\texttt{download\_assets}}

\begin{center}
  \textbf{\sig{download\_assets(f::Filing; destdir = ".")}}
\end{center}


\noindent Download the relative assets --- chiefly the embedded images --- that a
filing's HTML references, writing each next to the document under \texttt{destdir} so
a saved filing renders self-contained. The \texttt{src}/\texttt{href} attributes are
scanned and only relative URLs with a known asset extension (images, CSS, JS) are
taken, so links to sibling filings and in-page anchors are skipped; each asset is
fetched through the cached \texttt{fetch\_url} and written preserving any sub-path. The
download is best-effort (a reference that cannot be fetched is skipped) and the list
of filenames written is returned. \texttt{open\_filing} and \texttt{save\_filing} call it
for you; use it directly only to populate a directory yourself.


\subsection{Worked Example: The Filings Life-Cycle}
\label{sec:lifecycle-example}

\noindent The functions above compose into a complete workflow. The script below
walks the whole life-cycle on a real filing --- Walmart's latest Form 10-Q (chosen
over a tidier filer precisely because its Balance Sheet extracts a little roughly,
exercising the heuristics) --- using nothing but the public API: it resolves the
CIK, fetches the 10-Q, renders it, extracts the Balance Sheet, saves both the full
filing and the Balance Sheet to disk, reloads each from disk and shows it in the
browser, \emph{searches the filing's prose} for a phrase, and finally
\emph{validates} its headline figures against Yahoo Finance (\S\ref{sec:validation}).

\begin{lstlisting}
julia> using EDGAR
julia> set_user_agent("Your Name you@example.com")   

# 1. Find the company's CIK from its ticker.
julia> row = only(cik("WMT"; by = :ticker))

# 2. Fetch its latest Form 10-Q into memory.
julia> filing = first(filings_by_cik(row.cik; forms = "10-Q"))
julia> f = fetch_filing(row.cik, filing.accession)

# 3. Render the fetched filing in the browser.
julia> open_filing(f)

# 4. Extract the Balance Sheet from the filing HTML (f.content).
julia> balance_sheet = extract_section(f.content, ["Balance Sheet"])["Balance Sheet"]

# 5. Save the full 10-Q to disk (also downloads its images).
julia> path_10q = save_filing(f; destdir = "filings_demo")

# 6. Save the extracted Balance Sheet as a small standalone HTML page.
julia> path_bs = joinpath("filings_demo", "balance_sheet.html")
julia> write(path_bs, "<!doctype html><html><body><pre>" *
               balance_sheet * "</pre></body></html>")

# 7. Load the saved 10-Q from disk and show it in the browser.
julia> open_filing(path_10q)

# 8. Load the saved Balance Sheet from disk and show it in the browser.
julia> open_filing(path_bs)

# 9. Search the filing's prose: paragraphs mentioning a phrase, each located by index.
julia> hits = find_paragraphs(f, "supply chain")
julia> EDGAR._paragraphs(f.content)[hits[1].index]      # jump back to the matched paragraph

# 10. Validate the headline figures against Yahoo Finance (pulls the latest 10-K).
julia> using YFinance
julia> include(joinpath(pkgdir(EDGAR), "src", "sources", "yahoo_oracle.jl"))
julia> using .YahooOracle
julia> YahooOracle.validate(:sec, row.cik, "WMT")       # Assets/Equity/Revenue/NetIncome/OperCashFlow
\end{lstlisting}

\noindent Every step succeeds against the live filing; Table~\ref{tab:lifecycle}
records what each produces (the public API only, no internals).

\subsection{Interactive Extraction: \texttt{select\_section}}
\label{sec:select-section}

\sig{select\_section(f::Filing; timeout=1800) -> Selection}

\noindent Sometimes the region you want is easier to \emph{point at} than to name.
\texttt{select\_section} opens the rendered filing \texttt{f} in your browser with an
interactive picker and hands the region you choose back to Julia as a
\texttt{Selection}. A local HTTP server --- bound to \texttt{127.0.0.1} on a random
port, so nothing is exposed off the machine --- serves the document with a small
picker script injected, receives your pick, and shuts down as soon as one arrives or
\texttt{timeout} seconds elapse. (Pass a larger \texttt{timeout} if you expect to
browse for a while before choosing.)

\paragraph{Hover, widen, capture.} As you move the cursor the picker outlines the
element beneath it and a badge names what will be captured. A table is completely
covered by its own cells, so you can never hover the \htmltag{table} directly --- the
cursor always lands on a \htmltag{td}. Press \textbf{$\uparrow$} to widen the
selection to the parent element (and \textbf{$\downarrow$} to narrow); the highlight
\emph{sticks} as you press, so a stray mouse movement does not snap it back. Press
\textbf{Enter} (or click) to capture, or \textbf{Esc} to cancel.

\paragraph{The colour tells you what you will get.} The outline and badge are
colour-coded by the \emph{kind} of the candidate element, which is exactly what
determines how the capture is later exported. Widening from a number cell in a
financial statement cycles through:

\begin{center}\ttfamily
\htmltag{td}~\swatch{pickerpurple} $\to$ \htmltag{tr}~\swatch{pickerpurple} $\to$
\htmltag{tbody}~\swatch{pickerpurple} $\to$ \htmltag{table}~\swatch{pickergreen} $\to$
\htmltag{div}~\swatch{pickeramber} (wrapper)
\end{center}

\begin{table}[h]
\centering
\caption{What each highlight captures. The same block on screen, but a different
payload and a different \texttt{kind}.}
\label{tab:picker-kinds}
\begin{tabular}{@{}p{0.21\textwidth}p{0.10\textwidth}p{0.34\textwidth}p{0.25\textwidth}@{}}
\toprule
\textbf{Highlight} & \textbf{\texttt{kind}} & \textbf{What is captured} & \textbf{Good for} \\
\midrule
\swatch{pickergreen}~\htmltag{table} & \texttt{:table} &
  The clean \htmltag{table} --- header and body rows, with every XBRL fact inside. &
  The right pick: a structured Markdown table and resolved facts. \\
\swatch{pickeramber}~\htmltag{div} (wrapper) & \texttt{:mixed} &
  The table \emph{plus} the prose in its wrapper --- the
  ``(Amounts in millions\ldots)'' caption, footnotes. &
  A table together with its caption and notes (context for RAG). \\
\swatch{pickerpurple}~\htmltag{tbody} & \texttt{:prose} &
  The body rows only, as text --- \emph{not} parsed as a table, and it can omit the
  column headers that sit above \htmltag{tbody}. &
  Rarely what you want for a table. \\
\swatch{pickerpurple}~\htmltag{tr} / \htmltag{td} & \texttt{:prose} &
  One row / one cell, as text. & A single line or figure. \\
\bottomrule
\end{tabular}
\end{table}

\noindent So even though \htmltag{tbody} (purple) and \htmltag{table} (green) look
like the same block, the green one round-trips as a structured table --- with its
headers and facts --- while the purple \htmltag{tbody} comes back as a flat blob of
text with no columns. \emph{That} is why the colour coding matters: it tells you what
you will actually get, not just what is outlined.

\paragraph{Prose is a feature, not a mistake.} A purple (\texttt{:prose}) pick is not
a failed table pick --- it is its own use case. The narrative parts of a filing are
often exactly what you are after: Management's Discussion and Analysis, a risk factor,
a single footnote, the cover page. The picker captures those as readily as a table;
reach for green when you want a grid of numbers, and purple when you want the words.

\paragraph{Confirmation --- visual, audible, and in Julia.} On a successful capture the
toolbar reports what was taken (e.g.\ ``Captured TABLE --- 23 rows $\times$ 3 cols'', or
``\ldots\ 1{,}214 chars'' for prose), and a short synthesised ``shutter'' click plays ---
generated with the browser's Web Audio API, so no sound file is shipped. Back in Julia,
\texttt{select\_section}/\texttt{select\_sections} log a one-line \texttt{@info} summary on
return (kind, selector, size), so you can see the pick landed without inspecting the value.

\paragraph{Capturing several regions: \texttt{select\_sections}.} To grab more than one
region in a single sitting --- the income statement, the balance sheet, a footnote --- use
the plural form:

\sig{select\_sections(f::Filing; timeout=1800) -> Vector\{Selection\}}

\noindent It behaves like \texttt{select\_section}, except each \textbf{Enter}/click
\emph{adds} the highlighted region (the toolbar keeps a running count) and \textbf{Esc}
\emph{finishes}, returning everything as a \texttt{Vector\{Selection\}}. Repeated picks of
the same element are de-duplicated by selector, and finishing without picking anything
returns an empty vector (it does not throw, unlike the singular form). The two functions
keep distinct, fixed return types --- \texttt{Selection} versus \texttt{Vector\{Selection\}}
--- rather than overloading one with a mode flag. Note the difference in \textbf{Esc}: in
\texttt{select\_section} it \emph{cancels} (nothing was chosen, so the call throws); in
\texttt{select\_sections} it \emph{finishes} (returns what you have so far).

\paragraph{Previewing a pick: \texttt{open\_filing(sel)}.} A \texttt{Selection} is not a
\texttt{Filing}, so the \texttt{Filing} verbs do not apply to it --- \texttt{save\_filing(sel)}
is a \texttt{MethodError}. There is, however, a \texttt{Selection} method of
\texttt{open\_filing} for a quick visual check:

\sig{open\_filing(sel::Selection) -> String}

\noindent It wraps the captured HTML in a minimal page --- a \htmltag{base} so the
fragment's relative images still resolve to the SEC Archives, plus a provenance header
(filer, accession, selector) --- writes it to a throwaway temporary file and opens it,
returning the path. To \emph{keep} a selection (as Markdown, facts, or a database row), use
the export layers rather than \texttt{save\_filing}.

\paragraph{Exporting to Markdown: \texttt{markdown}.} Turn a pick into Markdown --- a
structured table becomes a Markdown table, prose becomes text --- ready to drop into a
document or hand to a language model:

\sig{markdown(sel::Selection; provenance=true) -> String}

\noindent The faithful capture grid (Step 2.1) is cleaned up here. SEC iXBRL tables put
the \texttt{\$} marker in its own column on only some rows (the first of a section,
totals, per-share lines), which shifts the value from one column to another row by row;
\texttt{markdown} drops the empty and lone-\texttt{\$} cells in each row and re-packs, so
the columns line up again, and uses the first surviving row as the header. With
\texttt{provenance = true} (the default) a blockquote recording the source --- CIK,
accession, URL, selector --- is prepended, so the output is self-describing for
citation/RAG (Step 2.3); pass \texttt{provenance = false} for just the table. Walmart's
income statement renders as (abridged):

\begin{verbatim}
> Source: SEC EDGAR -- CIK 0000104169, accession 0000104169-26-000102 (table)
> Selector: `div:nth-of-type(52) > table:nth-of-type(1)`

| Three Months Ended April 30, |  |  |
| --- | --- | --- |
| (Amounts in millions, except per share data) | 2026 | 2025 |
| Net sales | 175,684 | 163,981 |
| Total revenues | 177,751 | 165,609 |
| Interest income | (79) | (93) |
\end{verbatim}

\begin{lstlisting}
f    = fetch_filing(104169, "0000104169-26-000102")  # Walmart 10-Q
sel  = select_section(f)        # hover a number, press up to <table> (green), Enter
sel.kind                        # :table
open_filing(sel)                # preview exactly what you captured
print(markdown(sel))            # Markdown table under a provenance header

sels = select_sections(f)       # pick several regions, then Esc to finish
length(sels)                    # how many you captured
\end{lstlisting}

\paragraph{Extracting XBRL facts: \texttt{facts}.} When the filing is inline XBRL, the
picker also resolves the machine-readable \emph{facts} tagged inside the selection
against the document's \texttt{<ix:header>} (its contexts and units). \texttt{facts}
assembles them into a Tables.jl row table --- the hardened fact schema:

\sig{facts(sel::Selection) -> Vector\{FactRow\}}

\noindent Each row carries \texttt{cik}, \texttt{accession}, \texttt{statement},
\texttt{concept} (e.g.\ \texttt{us-gaap:Revenues}), \texttt{label}, the \emph{normalised}
\texttt{value} (\texttt{displayed} $\times\,10^{\mathrm{scale}}\times$ \texttt{sign}),
\texttt{unit} (\texttt{USD}, \texttt{shares}, \texttt{USD/shares}), \texttt{period\_start}/
\texttt{period\_end}, \texttt{is\_instant} (a balance-sheet instant vs an income-statement
flow), \texttt{dimensions} (JSON), \texttt{decimals}, the raw \texttt{context\_ref}/
\texttt{unit\_ref}, and \texttt{source\_selector}. Rows are de-duplicated on the natural
key \texttt{(accession, concept, context\_ref, unit\_ref)}. A prose-only selection yields
an \emph{empty} table --- no error. As a \texttt{Vector} of \texttt{NamedTuple}s it is a
Tables.jl source, so it renders with \texttt{PrettyTables} and feeds \texttt{CSV}, Arrow,
\texttt{DataFrames} or a database.

\begin{lstlisting}
sel = select_section(f)         # pick the income statement
using PrettyTables
pretty_table(facts(sel))        # the normalised facts as a table
\end{lstlisting}

\noindent\emph{Correctness.} The extraction is validated against the SEC's own
\texttt{companyfacts} API (\S\ref{sec:api-xbrl}): for Walmart's 10-Q, every fact picked
from the income statement (42) and the balance sheet (98) --- durations and instants,
across all units --- equals the API's value for the same concept, period and unit. The
picked numbers are the reported numbers.

\subsection{Exporting a Selection: iXBRL, Markdown, Facts JSON, DuckDB}
\label{sec:export-layers}

A picked \texttt{Selection} exports at three levels of abstraction --- \emph{preserve} it,
\emph{read} it, or \emph{analyse} it --- across four formats (Table~\ref{tab:export-layers}).
\texttt{save\_selection} is the one-stop ``Export As'' menu; each format is also available
on its own.

\begin{table}[h]
\centering
\caption{The export layers of a \texttt{Selection}.}
\label{tab:export-layers}
\begin{tabular}{@{}p{0.13\textwidth}p{0.14\textwidth}p{0.30\textwidth}p{0.30\textwidth}@{}}
\toprule
\textbf{Layer} & \textbf{Format} & \textbf{Function} & \textbf{Purpose} \\
\midrule
Presentation & iXBRL HTML & \texttt{sel.html} / \texttt{open\_filing} & Preserve the fragment exactly (lossless) \\
Presentation & Markdown & \texttt{markdown(sel)} & Documentation, notes, RAG \\
Semantic & Facts JSON & \texttt{facts\_json(sel)} & Portable XBRL semantics; LLM input; old-XBRL bridge \\
Analytical & DuckDB & \texttt{to\_duckdb(sel, db)} & A queryable fact warehouse \\
\bottomrule
\end{tabular}
\end{table}

\sig{save\_selection(sel::Selection; as, dir=".", db=nothing) -> String | Int}

\noindent \texttt{as} is \texttt{:ixbrl}, \texttt{:markdown}, \texttt{:facts} or
\texttt{:duckdb}. The first three write a file under \texttt{dir} (named
\texttt{<accession>\_<selector-slug>.<ext>}) and return its path; \texttt{:duckdb} appends
to a warehouse (default \texttt{<dir>/facts.duckdb}) and returns the number of rows inserted.

\begin{lstlisting}
sel = select_section(f)                            # pick the income statement
save_selection(sel; as = :ixbrl,    dir = "out")   # lossless fragment .ixbrl.html
save_selection(sel; as = :markdown, dir = "out")   # .md
save_selection(sel; as = :facts,    dir = "out")   # .facts.json
using DuckDB
save_selection(sel; as = :duckdb,   dir = "out")   # rows appended to out/facts.duckdb
\end{lstlisting}

\paragraph{Facts JSON --- the semantic layer.} \texttt{facts\_json} serialises the resolved
facts to a portable JSON document: a provenance header plus a \texttt{facts} array, values
already normalised. It is the convenient working representation of the iXBRL semantics ---
clean to feed a language model, cheap to re-query, and (carrying no HTML) a \emph{common
shape across modern inline XBRL, old classic XBRL, and extracted fragments}.
\texttt{read\_facts\_json} reads it back into a \texttt{Selection}, so it round-trips and
flows on to \texttt{facts}/\texttt{to\_duckdb} --- which is also how a pre-iXBRL filing,
with no rendered HTML, enters the same pipeline.

\sig{facts\_json(sel::Selection; pretty=true) -> String}
\sig{read\_facts\_json(source) -> Selection}

\begin{verbatim}
{ "version": 1,
  "cik": "0000104169", "accession": "0000104169-26-000102",
  "selector": "div:nth-of-type(52) > table:nth-of-type(1)", "kind": "table",
  "facts": [
    { "concept": "us-gaap:Revenues", "label": "Total revenues",
      "value": 177751000000, "unit": "USD",
      "period_start": "2026-02-01", "period_end": "2026-04-30",
      "is_instant": false, "dimensions": {}, "decimals": -6,
      "context_ref": "c-1", "unit_ref": "usd" } ] }
\end{verbatim}

\paragraph{DuckDB --- the analytical warehouse.} \texttt{to\_duckdb} writes into a DuckDB
warehouse (a package extension --- available after \texttt{using DuckDB}): a single
\texttt{.duckdb} file holding three tables joined by \texttt{accession} ---
\texttt{documents} (the lossless iXBRL HTML, Layer 1, written by
\texttt{to\_duckdb(f::Filing, db)}), \texttt{extractions} (the Facts JSON snapshot of each
pick or filing, Layer 2), and \texttt{facts} (the rows, Layer 3) --- plus an
\texttt{edgar\_meta} schema marker. The \texttt{facts} table is the canonical sink every
source maps into: the picker (\texttt{source='picker'}, with \texttt{source\_selector}
tracing each row back to the picked region) and whole-filing extraction
(\texttt{source='filing'}); the \texttt{form}/\texttt{fy}/\texttt{fp}/\texttt{frame} columns
are reserved for structured-data sources. Its primary key is each fact's \emph{semantic
identity} \texttt{(cik, accession, concept, unit, period, dimensions)} --- not the
document-internal \texttt{context\_ref}/\texttt{unit\_ref}, kept only as provenance --- so
rows are inserted \texttt{ON CONFLICT DO NOTHING}: re-importing a filing is idempotent, and
the same fact from two sources collapses to one row. You grow the warehouse filing by filing,
and every fact joins back to its source document and extraction.

\sig{to\_duckdb(data, db; table="facts") -> Int}

\noindent \texttt{statement\_view} pivots the long fact table back into a \emph{wide}
statement --- one row per concept/label, one column per period --- and, because the warehouse
may hold many filings, \emph{stitches} the statement across them:

\sig{statement\_view(db; statement=nothing, accession=nothing, consolidated=true, months=nothing, by=:concept) -> Vector\{NamedTuple\}}

\noindent \texttt{statement} restricts to one financial statement (e.g.\ \texttt{"IncomeStatement"};
needs facts ingested with \texttt{classify=true}); \texttt{months} is \emph{smart period
selection} --- keep only durations of about that many months (\texttt{3} quarterly, \texttt{12}
annual) plus instants, so periods sharing an end date do not collide; and
\texttt{by=:standard\_concept} groups by the standardized concept (\S\ref{sec:export-layers}) for
cross-company comparison. For example, a quarterly income statement stitched across several
10-Qs:

\begin{lstlisting}
using DuckDB, PrettyTables
archive_filings(104169, "wmt.duckdb"; forms = "10-Q", limit = 4, classify = true)
pretty_table(statement_view("wmt.duckdb"; statement = "IncomeStatement", months = 3,
                            by = :standard_concept))
\end{lstlisting}

\noindent The result is a Tables.jl row table (the period dates are the column names).

\paragraph{Bulk extraction: \texttt{facts(::Filing)} and \texttt{archive\_filings}.} The picker
is for curated, one-at-a-time selection; for whole filings there is a native, browser-free
extractor. \texttt{facts(f::Filing)} reads \emph{every} XBRL fact from a filing --- its inline
XBRL (\texttt{<ix:nonFraction>}) or a classic \texttt{.xml} instance --- as the same row table.
It honours the iXBRL display transforms: a dash shown via \texttt{ixt:fixed-zero} is read as the
value \texttt{0}, and a spelled-out number (\texttt{ixt-sec:numwordsen}, e.g.\ a ``\,No\,'' par
value or ``Forty-two'') is parsed from its words.

\sig{facts(f::Filing; classify=false, labels=false) -> Vector\{FactRow\}}

\noindent and \texttt{archive\_filings} bulk-archives a filer's filings into the warehouse in
one pass: it lists them with \texttt{filings\_by\_cik}, then stores each document and (with
\texttt{facts=true}) its extracted facts (\texttt{source='filing'}) and a filing-level snapshot,
reusing one connection and skipping any filing that fails to fetch.

\sig{archive\_filings(cik, db; forms=nothing, facts=true, classify=false, labels=false, kind=:auto, limit=nothing) -> NamedTuple}

\begin{lstlisting}
using DuckDB
archive_filings(104169, "wmt.duckdb"; forms = "10-Q", limit = 4)
# -> (filings = 4, documents = 4, facts = ...)   # then query across filings
\end{lstlisting}

\paragraph{Statement classification.} The \texttt{statement} column (\texttt{IncomeStatement},
\texttt{BalanceSheet}, \texttt{CashFlow}, \texttt{Equity}, \texttt{ComprehensiveIncome}, the
fund/BDC statements \texttt{ScheduleOfInvestments} and \texttt{FinancialHighlights}, or
\texttt{CoverPage}) records which financial statement a fact belongs to. It is filled from the
\emph{authoritative} source --- the filing's own presentation linkbase (\texttt{*\_pre.xml}),
which groups concepts into statement sections --- so it is not a heuristic guess. Pass
\texttt{classify=true} to \texttt{facts(::Filing)}, \texttt{archive\_filings},
\texttt{to\_duckdb(f::Filing, db)}, or the interactive \texttt{select\_section} /
\texttt{select\_sections} to fill it (one extra fetch of the linkbase); concepts that
appear only in notes are left blank. The map is also available directly:

\sig{statement\_map(f::Filing) -> Dict\{String, String\}}

\paragraph{Multi-homed concepts.} A concept frequently belongs to \emph{more than one} statement:
\texttt{StockholdersEquity} appears in both the balance sheet and the statement of equity;
\texttt{NetIncomeLoss} appears in the income statement, the cash-flow reconciliation, the statement
of comprehensive income \emph{and} the equity roll-forward. The single \texttt{statement} column
records only the \emph{primary} (highest-priority) section, so every fact also carries a
\texttt{statements} column --- the JSON array of \emph{all} sections it belongs to, primary first (so
\texttt{statement} equals \texttt{statements[1]}). Without it, a literal \texttt{statement ==
"Equity"} filter would miss the \texttt{StockholdersEquity} totals (which are primarily the balance
sheet's). Accordingly the DuckDB \texttt{statement\_view} is \emph{membership-aware}: querying
\texttt{statement = "Equity"} returns every fact whose \texttt{statements} set contains \texttt{Equity}
--- the equity movements \emph{and} the multi-homed totals --- reconstructing the full statement.

The \texttt{statements} set also captures \emph{combined} statements --- one role serving two, such as
a ``Statement of Operations and Comprehensive Income'' (common for REITs and many foreign filers).
The role classifies to a single primary, but a curated \emph{key-anchor} concept belongs to its
statement by definition regardless of packaging: \texttt{ComprehensiveIncomeNetOfTax} is comprehensive
income, \texttt{NetIncomeLoss} is the income statement. So a combined statement's facts carry
\emph{both} memberships, and querying \texttt{statement = "ComprehensiveIncome"} (or
\texttt{"IncomeStatement"}) finds the combined filer directly --- the \texttt{select\_statement}
resolver remains for row tables that lack the membership column.

\noindent Some filers (typically inline-only filings) ship \emph{no} loose presentation
linkbase. For those, classification falls back automatically to the SEC-generated
\texttt{FilingSummary.xml} and the rendered statement R-files --- present for \emph{every}
XBRL filing --- so \texttt{classify=true} works across filers rather than silently returning
nothing. Only the face statements are read: the classifier scores each report's role name, its
concepts and --- for the FilingSummary path --- its \texttt{LongName} category
(\texttt{Statement} vs \texttt{Disclosure}), with notes/details scoring as disqualifying. So a
generically named detail R-file (e.g. ``Comprehensive Income Statements (Detail)'', whose role still
embeds the word \emph{income statement}) is not mistaken for the statement itself. The map is empty
(and a warning is emitted) only if \emph{both} sources are missing.

\paragraph{Combined statements and the query-time resolver.} Classification reflects the filing's
\emph{actual} structure, not an idealised one --- and that occasionally bites. Some filers (many
foreign IFRS issuers, and a few domestic ones) present a single \emph{combined} ``Statement of Profit
or Loss and Other Comprehensive Income'' rather than a standalone income statement. For those, the
net-income line is correctly tagged \texttt{ComprehensiveIncome} --- that is the section the filing
puts it in --- so a literal filter for \texttt{statement == "IncomeStatement"} returns \emph{nothing}.
This is faithful, not a bug: silently re-tagging the fact would throw away the true fact that it lives
in the combined statement. To ask for the income statement \emph{regardless} of how a filer arranged
it, use the query-time resolver:

\sig{select\_statement(rows, statement) -> rows}

\noindent It returns the rows for \texttt{statement} directly when that section exists, and otherwise
falls back to the section that \emph{subsumes} it --- income $\to$ comprehensive income $\to$ equity ---
but only when that section actually carries the requested type's anchor concepts, so a pure
other-comprehensive-income section is never mistaken for the income statement. The same caveat applies
to the DuckDB \texttt{statement\_view}: querying \texttt{statement = "IncomeStatement"} for a
combined-statement filer returns no rows --- query \texttt{"ComprehensiveIncome"} instead, or run the
facts through \texttt{select\_statement} before loading them. The rule of thumb: the \texttt{statement}
column tells you \emph{where the filer put a number}; \texttt{select\_statement} tells you \emph{which
section answers your question}.

\paragraph{Statements filed as a note.} A related case: some filers present a whole statement --- most
often the statement of changes in equity --- \emph{only} as a note/detail disclosure, never as an XBRL
face section. Classification then leaves it blank, faithfully: the note's ``\ldots Details'' or
text-block role is not a face statement. To recover it on demand:

\sig{reconstruct\_from\_notes(f::Filing, statement) -> Vector\{FactRow\}}

\noindent finds the note role whose \emph{intent} is \texttt{statement} (a relaxed classification that
ignores the note/detail markers) and returns its facts re-tagged to \texttt{statement}. The result is
explicitly \textbf{reconstructed, not classified}: every row is marked \texttt{source\_selector =
"reconstructed:<role>"} (directly extracted facts carry an empty \texttt{source\_selector}), so the two
are never confused. It is opt-in --- ordinary \texttt{facts(f; classify=true)} stays faithful and never
includes these. The logic is jurisdiction-agnostic (a two-argument
\texttt{reconstruct\_from\_notes(pre\_xml, rows, statement)} takes any presentation linkbase and facts
table); the \texttt{Filing} method fetches both for an SEC filing.

\paragraph{Negated presentation labels.} A filing's presentation linkbase may show a concept with a
\emph{negated} preferred label (\texttt{negatedLabel}, \texttt{negatedTerseLabel}, \ldots), which flips
the sign for display --- so the \emph{rendered} statement shows the opposite of the stored value
(treasury stock as a contra-equity; some filers even store operating cash flow negated). With
\texttt{classify=true}, \texttt{facts(::Filing)} honours these labels and flips the affected facts'
signs, so a value matches the statement as the company reports it. With \texttt{classify=false} you get
the \emph{raw} stored fact value (identical to the SEC \texttt{companyfacts} API), unnegated. Filers with
no presentation linkbase (the FilingSummary fallback) carry no labels, so this does not apply to them.

\paragraph{Native labels.} The picker reads a fact's human-readable \texttt{label} off the
rendered table row; the browser-free extractor has no rendered page, so it reads the filing's
\emph{label linkbase} (\texttt{*\_lab.xml}) instead --- the authoritative \texttt{concept => label}
map (preferring the standard label, then terse, then verbose). Pass \texttt{labels=true} to
\texttt{facts(::Filing)}, \texttt{archive\_filings} or \texttt{to\_duckdb(f::Filing, db)} to fill
the \texttt{label} column (one extra fetch); without it native facts have an empty label. The map
is also available directly:

\sig{label\_map(f::Filing) -> Dict\{String, String\}}

\paragraph{Calculation relationships.} A filing's \emph{calculation linkbase}
(\texttt{*\_cal.xml}) is the arithmetic of each statement: which concepts sum into which, with
a signed weight (\texttt{+1} added, \texttt{-1} subtracted). \texttt{calculations} returns it as
a Tables.jl row table of \texttt{(statement, parent, child, weight)}.

\sig{calculations(f::Filing) -> Vector\{NamedTuple\}}

\noindent This is the authoritative \emph{how-it-rolls-up} structure --- use it to validate that
children sum to their parent (a data-quality check) or to read a line's contribution sign. It
does \emph{not} rewrite the stored fact values: those are XBRL-canonical and validated against the
SEC \texttt{companyfacts} API, and the printed sign of a line depends on its parent, which is
statement-specific. For Walmart, \texttt{us-gaap:OperatingIncomeLoss} =
\texttt{Revenues}\,(+1)\,$-$\,\texttt{CostOfRevenue}\,(-1)\,$-$\,\texttt{SGA}\,(-1), and the
children indeed sum to the reported operating income.

\paragraph{Concept standardization (pluggable).} Each fact row carries a
\texttt{standard\_concept}: the issuer's \texttt{concept} mapped to a common name so facts can be
grouped and compared across companies (the original \texttt{concept} and \texttt{label} are
always preserved --- the dual-label approach). A standardization mapping is, however, an
\emph{opinionated} artifact --- two distinct lines (Net sales vs.\ Total revenues) must not
collapse to one --- so EDGAR.jl ships \textbf{no} default: until you select a mapping with
\texttt{set\_standardizer}, \texttt{standard\_concept} is \texttt{nothing}.

\sig{standardize(concept) -> Union\{String, Nothing\}}
\sig{set\_standardizer(mapping)}

\noindent \texttt{mapping} is a \texttt{Dict} of \texttt{concept => standard\_concept}, a
function \texttt{concept -> Union\{String, Nothing\}}, or \texttt{:none}. Supply your own, or
select one of the mappings EDGAR.jl plans to offer, which fall into two kinds:
\begin{itemize}
\item \textbf{Reference} --- the us-gaap taxonomy and the SEC Financial Statement Data Sets give
  \emph{canonical} concepts and labels, but do \emph{not} collapse synonyms (two tags for
  ``revenue'' stay distinct);
\item \textbf{Community} --- a curated mapping that collapses synonyms for cross-company
  comparison, at the cost of being opinionated. EDGAR.jl \emph{bundles} one:
  \texttt{set\_standardizer(:edgartools)} loads the edgartools mapping (vendored, MIT-licensed
  and attributed --- see \texttt{src/data/edgartools\_concept\_mappings.NOTICE.md}), which maps,
  for example, \texttt{us-gaap:Revenues} to \texttt{Revenue} but
  \texttt{us-gaap:RevenueFromContractWithCustomer\ldots} to the \emph{distinct}
  \texttt{Contract Revenue}, so Net sales and Total revenues do not collapse.
\end{itemize}

\noindent The bundled edgartools mapping is also available directly --- as a plain
\texttt{concept => standard\_concept} \texttt{Dict} --- for inspection or to use as a base you
extend before passing to \texttt{set\_standardizer}:

\sig{edgartools\_mapping() -> Dict\{String, String\}}

\begin{lstlisting}
set_standardizer(:edgartools)               # the bundled community mapping (MIT, attributed)
standardize("us-gaap:Revenues")             # "Revenue"
standardize("us-gaap:RevenueFromContractWithCustomerExcludingAssessedTax")  # "Contract Revenue"
set_standardizer(Dict("xx:Foo" => "Bar"))   # or supply your own
set_standardizer(:none)                     # the default: no standardization
\end{lstlisting}

\noindent The bundled edgartools mapping is a point-in-time snapshot. Maintainers can re-vendor it
from upstream with \texttt{julia --project scripts/refresh\_standardizer.jl} (optionally passing a
tag or commit); the script validates the download as JSON before it replaces the bundled copy. See
\texttt{src/data/edgartools\_concept\_mappings.NOTICE.md}.

\paragraph{No extra sinks needed.} Parquet, CSV and SQLite are deliberately \emph{not}
separate exports. A fact table is a Tables.jl source, so \texttt{CSV.write(path, facts(sel))},
\texttt{Arrow.write(\ldots)} and \texttt{SQLite.load!(\ldots)} already take it in one line;
and once the facts are in DuckDB, \texttt{COPY facts TO 'f.parquet' (FORMAT PARQUET)} or
\texttt{ATTACH 'f.sqlite' (TYPE SQLITE)} export them with a single SQL statement. Wrapping
these would only add dependencies for no gain.

\subsection{\texttt{structured\_document}}

\begin{center}
\textbf{\sig{structured\_document(pdf\_path; pages=nothing, ocr=false, doc\_id=<stem>,
jurisdiction=nothing, language=nothing, company=nothing, report\_type=nothing, fiscal\_year=nothing,
currency=nothing, framework=nothing) -> StructuredDocument}}
\end{center}

\noindent Parse a born-digital PDF into a \texttt{StructuredDocument} --- an ordered set of
\textbf{sections} (heading tree), \textbf{text blocks} (prose), \textbf{tables} (with their cells) and
\textbf{figures}, each carrying \texttt{(page, bbox)} provenance and a global reading-order index, plus
document metadata. The original language is stored verbatim. \texttt{pages} is an optional 1-based
\texttt{(first, last)} range; \texttt{ocr} turns on OCR (needed only for a broken text layer, e.g.\
Japanese EDINET); the metadata keywords seed fields a per-jurisdiction profile would otherwise fill.
Statement classification (\emph{which} table is the balance sheet) is a later, separate step --- the parser
emits structure only.

\begin{lstlisting}
julia> using EDGAR, PythonCall
julia> sd = structured_document("UK-TescoFR2024.pdf"; jurisdiction = "GB", language = "en",
                                framework = "IFRS", fiscal_year = 2024)
StructuredDocument(UK-TescoFR2024: 9 sections, 25 text, 6 tables, 2 figures)
\end{lstlisting}

\subsection{\texttt{persist\_document}}

\begin{center}
\textbf{\sig{persist\_document(sd::StructuredDocument; root="\textasciitilde/RegulatoryReports") -> String}}
\end{center}

\noindent Write the document family to the filesystem under \texttt{root/derived/<doc\_id>/}:
\texttt{structured.json} (the canonical record), \texttt{document.md} (a Markdown render), and
\texttt{tables/<id>.csv} per table. Returns the derived-folder path. (Loading the repository DuckDB is a
separate step; see the schema design in \texttt{docs/dev/pdf-repository-schema.md}.)

\begin{lstlisting}
julia> persist_document(sd)
"/Users/you/RegulatoryReports/derived/UK-TescoFR2024"
\end{lstlisting}

\subsection{\texttt{markdown}, \texttt{write\_structured\_document}, \texttt{read\_structured\_document}}

\begin{center}
\textbf{\sig{markdown(sd::StructuredDocument) -> String}}
\textbf{\sig{write\_structured\_document(sd::StructuredDocument, path)}}
\textbf{\sig{read\_structured\_document(path) -> StructuredDocument}}
\end{center}

\noindent \texttt{markdown(sd::StructuredDocument)} renders the document (headings, prose, pipe tables) in
reading order --- the human/RAG view. \texttt{write\_structured\_document(sd, path)} writes just the
canonical JSON to a chosen path, and \texttt{read\_structured\_document(path)} reads it back into a
\texttt{StructuredDocument} (so the repository loader below can run from persisted JSON, without
re-parsing the PDF and without PythonCall).

\subsection{\texttt{to\_repository}}

\begin{center}
\textbf{\sig{to\_repository(sd\_or\_json\_path, db="\textasciitilde/RegulatoryReports/regulatory-reports.duckdb")
-> NamedTuple}}
\end{center}

\noindent Load a \texttt{StructuredDocument} (or a \texttt{structured.json} path) into the DuckDB
\textbf{document repository}: the tables \texttt{documents}, \texttt{sections}, \texttt{text\_blocks},
\texttt{tables}, \texttt{table\_cells}, \texttt{figures} (plus \texttt{translations} and a \texttt{facts}
stub), and the referencing \emph{views} \texttt{v\_cell\_context}, \texttt{v\_section\_path} and
\texttt{v\_fact\_provenance}. The load is \textbf{idempotent} per \texttt{doc\_id} (re-loading replaces the
document's rows), and returns the inserted row counts. One DuckDB file indexes every report, so SQL and
full-text search (DuckDB's FTS over \texttt{text\_blocks}) work across the whole corpus. The full schema is
in \texttt{docs/dev/pdf-repository-schema.md}. \textbf{Available only after \texttt{using DuckDB}} (package
extension).

\begin{lstlisting}
julia> using EDGAR, DuckDB
julia> to_repository(sd)                       # or: to_repository("…/structured.json", db)
(sections = 9, text_blocks = 25, tables = 6, table_cells = 1121, figures = 2)
\end{lstlisting}

\noindent The views answer ``where does this number come from?'' directly --- every cell/fact traces to
its table and section/subsection:

\begin{lstlisting}
julia> using DuckDB: DBInterface
julia> con = DBInterface.connect(DuckDB.DB, expanduser("~/RegulatoryReports/regulatory-reports.duckdb"));
julia> DBInterface.execute(con,
           "SELECT section_id, page FROM v_cell_context WHERE text = '11,671'")
# → ("UK-TescoFR2024:s7", 133)   -- the Group balance sheet
\end{lstlisting}

\subsection{\texttt{classify\_tables!} and the table-class taxonomy}

\begin{center}
\textbf{\sig{classify\_tables!(db; doc\_id=nothing) -> Dict\{String,Int\}}}
\end{center}

\noindent Tag every repository table with a class: set \texttt{kind} (\texttt{statement} /
\texttt{descriptive}) and, for statements, \texttt{statement\_type}. It matches each table's heading ---
trying, in order, its caption, its section title, the nearest same-page heading block, and the
\textbf{PDF-outline entry} covering its page (§\ref{sec:pdf-classification}) --- against an \emph{open},
multilingual registry of table classes. Optionally restrict to one \texttt{doc\_id}; returns counts per
class. \textbf{Available only after \texttt{using DuckDB}.}

\begin{lstlisting}
julia> using EDGAR, DuckDB
julia> classify_tables!(; doc_id = "FR-TotalEnergiesFR2023")
Dict("balance_sheet"=>2, "income_statement"=>1, "cash_flow"=>1, "equity_changes"=>1, "descriptive"=>3)
\end{lstlisting}

\noindent The built-in taxonomy (\texttt{TABLE\_CLASSES}) covers the four core statements ---
\texttt{balance\_sheet}, \texttt{income\_statement}, \texttt{cash\_flow}, \texttt{equity\_changes} ---
\emph{plus} \texttt{fund\_portfolio} (a fund's \emph{schedule of investments} / portfolio holdings),
included precisely to show the registry is \textbf{not} financial-statement-locked. So fund portfolio
holdings classify out of the box --- and not only from PDFs: it is validated on a Vanguard~500 annual
report, a RiverNorth multi-fund report, and a Fidelity \emph{Contrafund} N-CSR (HTML). Other periodic
quantitative tables (a loan book, production volumes, \dots) are added the same way, with
\texttt{register\_table\_class!} and no change to the classifier or the schema.
\texttt{classify\_table\_class(heading)} is the underlying pure matcher (returns the
\texttt{statement\_type} key or \texttt{nothing}).

\begin{lstlisting}
julia> classify_tables!(; doc_id = "US-Vanguard500FR2023")   # the Schedule of Investments
Dict("fund_portfolio" => 9, "descriptive" => 24)

julia> register_table_class!("loan_book", "Loan portfolio",   # add a further class, no schema change
                             [r"loan portfolio"i, r"portefeuille de prêts"i])
\end{lstlisting}

\noindent (This is the document-first \emph{PDF/HTML} path. The XBRL/structured-data fund disclosures ---
N-PORT, 13F --- noted elsewhere as ``not yet implemented'' are a separate route; the path here extracts the
holdings \emph{tables} from the report document.)

\paragraph{Taxonomy helpers.}
\begin{center}
\textbf{\sig{register\_table\_class!(key, description, patterns::Vector\{Regex\}) -> TableClass}}
\textbf{\sig{classify\_table\_class(heading) -> Union\{String, Nothing\}}}
\end{center}

\noindent \texttt{register\_table\_class!} prepends a new class to the registry \texttt{TABLE\_CLASSES}
(so it takes precedence) and returns it. \texttt{classify\_table\_class} is the pure matcher used by
\texttt{classify\_tables!}: it returns the \texttt{statement\_type} key of the first class whose patterns
match \texttt{heading}, or \texttt{nothing} (a descriptive table).

\subsection{company\_concept}

\sig{company\_concept(cik, taxonomy, tag)}

\noindent One XBRL concept over time for a single filer, from
\texttt{/api/xbrl/companyconcept/} --- lighter than \texttt{company\_facts} when you
want a single line item. Observations live under \texttt{.units} keyed by unit (e.g.

\subsection{xbrl\_frames}

\sig{xbrl\_frames(taxonomy, tag, unit, period)}

\noindent One XBRL concept for one period across \emph{every} filer that reported

for o in filter(o -> o.form == "10-K", concept.units.USD)
    println(o.fy, "  ", o.val)
end

\section{Caching and runtime configuration}\label{sec:caching}

The caching layer is shared by every system; DART is just the
case that most needs tuning. The \texttt{cache} keyword of \texttt{set\_config} selects where the cache
lives and how long it survives: \texttt{:temporary} (default --- an ephemeral per-process directory,
deleted on exit), \texttt{:persistent} (kept in \texttt{\textasciitilde/.cache/EDGAR.jl} across sessions,
pruned past \texttt{cache\_max\_age}), or \texttt{:off} (no caching). Two \textbf{independent} time limits
apply: \texttt{cache\_ttl} (default 24\,h) is \emph{freshness} --- how long a cached response is reused
before re-fetching --- while \texttt{cache\_max\_age} (default 7\,days) is \emph{retention} before a file is
pruned; \texttt{cache\_max\_size} (default 10\,MB) caps a single response. \texttt{set\_cache\_policy(system;\
cache)} overrides the global mode for one \texttt{FilingSystem}, taking precedence over \texttt{set\_config}
for that system only --- the mechanism DART uses for its slow endpoints (\S\ref{sec:dart-caching}).

\begin{longtable}{@{}p{0.46\textwidth}p{0.50\textwidth}@{}}
\toprule
\textbf{Function} & \textbf{Purpose} \\
\midrule
\endhead
\texttt{set\_config(; cache, cache\_dir, cache\_ttl, cache\_max\_size, cache\_max\_age, host\_whitelist,
  allow\_file, user\_agent)} & Override the global runtime configuration (only the keywords you pass
  change). \\
\texttt{set\_cache\_policy(system; cache)} & Override the cache mode for a single \texttt{FilingSystem}. \\
\texttt{clean\_cache()} & Prune the cache on demand. \\
\texttt{cache\_metrics()} & Inspect hit/miss/request/byte counters. \\
\texttt{cache\_path\_for(url)} & The on-disk cache path for a given URL. \\
\bottomrule
\end{longtable}

\end{lstlisting}

\chapter{EDGAR \textemdash{} U.S.\ SEC}
\label{sys:edgar}

EDGAR (\emph{Electronic Data Gathering, Analysis, and Retrieval}) is the U.S.\ Securities and
Exchange Commission's filing system, and the \texttt{FilingSystem} that \texttt{EDGAR.jl} implements
in full --- discovery, fetch and parse. Every capability described in this chapter (form-level
section extraction, the search/lookup and XBRL structured-data APIs, the interactive picker, the
fact warehouse) is available for SEC filings today. In the code the concrete system type is
\texttt{SEC}\,\texttt{<:}\,\texttt{FilingSystem} (named \texttt{SEC} rather than \texttt{EDGAR} to
avoid clashing with the \texttt{EDGAR} module); a filer's identity is a CIK
(\texttt{EntityId(:cik,\ \ldots)}). The remaining chapters cover the other filing systems --- ESEF,
Companies House, EDINET, DART --- which reuse the same jurisdiction-agnostic core
(\S\ref{sec:architecture}) but are at earlier stages.

\section{Entities covered}\label{sec:edgar-entities}

Every filer on EDGAR --- whoever submits a filing --- is an \textbf{entity}, identified by a \textbf{CIK}
(Central Index Key, Appendix~\ref{sec:glossary}). An entity is not always an operating company: the SEC tags each
filer with an \texttt{entityType}, and the forms it files follow from that type. EDGAR's universe spans five
kinds of filer (Table~\ref{tab:edgar-entities}); \texttt{EDGAR.jl} extracts the financial statements of the
issuer types in full and reaches the rest for discovery and metadata, with anything not yet built flagged
\emph{not implemented yet}.

\centering
\small

\textbf{Entity type} & \textbf{Example} & \textbf{Primary forms} & \textbf{In \texttt{EDGAR.jl}} \\

\subsection{Domestic operating companies}
U.S.-incorporated public companies --- the bulk of EDGAR (\texttt{entityType} \texttt{"operating"}). They
file the periodic and current reports (10-K / 10-Q / 8-K), the proxy statement (DEF~14A) and registration
statements (S-1 / S-3). Their financial statements are extracted in full (\S\ref{sec:edgar-forms}).

\subsection{Foreign private issuers}
Non-U.S.\ companies whose securities trade in U.S.\ markets. They file the annual report on \textbf{Form
20-F} (the 10-K equivalent) and furnish interim material on \textbf{Form 6-K}; Canadian issuers under the
multi-jurisdictional disclosure system file \textbf{Form 40-F}. Examples: Toyota Motor, SAP~SE. Their
financial statements are extracted in full.

\subsection{Investment funds and institutional managers}
Registered investment companies --- mutual funds, ETFs and money-market funds (\texttt{entityType}
\texttt{"investment"}) --- and institutional investment managers. Funds file portfolio disclosures
(\textbf{N-PORT}, \textbf{N-MFP}); managers file \textbf{13F}. Discovery and filer metadata work today;
portfolio-level extraction is \emph{not implemented yet}.

\subsection{Insiders (officers and directors)}
Individuals subject to Section~16 reporting --- a company's officers and directors --- who report their
holdings and trades on \textbf{Forms 3, 4 and 5}, useful for tracking insider activity. Discovery works;
fact-level extraction of these forms is \emph{not implemented yet}.

\subsection{Significant owners}
Beneficial owners crossing the 5\,\% threshold, filing \textbf{Schedule 13D} (intent to influence) or
\textbf{Schedule 13G} (passive), useful for spotting activist stakes and takeover positions. Discovery
works; extraction is \emph{not implemented yet}.

\medskip
\noindent \textbf{Working with entities.} \texttt{EDGAR.jl} exposes entities through three functions.
\texttt{cik} maps a name or ticker to a CIK (covering entities that \emph{have} a ticker --- companies and
listed ETFs/funds); \texttt{profile(cik)} returns a filer's row-invariant record (its \texttt{name},
\texttt{entityType}, SIC industry, fiscal year-end, tickers, former names); and the \texttt{entity} column
of \texttt{filings\_by\_text} is simply that filer's name. So a typical workflow is: resolve the CIK
(\texttt{cik}), inspect the filer (\texttt{profile}), then pull its filings of the relevant form
(\texttt{filings\_by\_cik}):

\begin{lstlisting}
julia> id = only(cik("AAPL"; by = :ticker)).cik
"0000320193"
julia> profile(id).entityType
"operating"
julia> reports = filings_by_cik(id; forms = "10-K");
\end{lstlisting}

\medskip

\begin{itemize}
  \item \texttt{filings\_by\_cik}
    \begin{lstlisting}
    filings_by_cik(320193; forms = "8-K")          # Apple CIK = 320193

  \item \texttt{filings\_by\_text}

\subsection{Periodic and Current Reports}\label{big3}

\subsubsection{10-K: Annual Report}
The annual report, denoted 10-K, provides a comprehensive overview of a company's business and financial performance for the fiscal year.

\subsubsection{10-Q: Quarterly Report}
			
The quarterly report, denoted 10-Q, updates investors on the company's performance during a fiscal quarter. There is typically no Q4 10-Q because the annual 10-K covers the full year. Unlike a 10-K, the financial statements are usually reviewed but not fully audited.

\subsubsection{8-K: Current Report}

The current report, denoted 8-K, is filed whenever a material event occurs that investors should know about. Unlike 10-K and 10-Q filings, 8-K filings are event-driven and can be filed at any time. Common triggers include:
\begin{itemize}
  \item Acquisitions or mergers
  \item Bankruptcy
  \item CEO or CFO changes
  \item Director appointments or resignations
  \item Major contracts
  \item Earnings announcements
  \item Changes in auditors
  \item Delisting notices
\end{itemize}


\subsection{Foreign Companies}

\subsubsection{20-F: Annual Report}
The foreign-issuer equivalent of Form 10-K. Filed annually by foreign companies whose securities are traded in U.S. markets. Useful for understanding a foreign company’s business, risks, financial condition, and corporate governance. Examples include Toyota Motor Corporation and SAP SE.

\subsection{Corporate Governance}
\subsubsection{Proxy Statement (DEF 14A)}
Many researchers consider the Proxy Statement (DEF 14A)\footnote{\textbf{DEF} denotes Definitive and \textbf{14A} refers to proxy materials filed under Section 14(a) of the Securities Exchange Act.} the best source of information on executive compensation, directors, and corporate governance. Typical contents include:
\begin{itemize}
\item Executive compensation
\item Director biographies
\item Board composition
\item Related-party transactions
\item Shareholder proposals
\end{itemize}


\subsection{Tender Offers and Mergers}
\subsubsection{Schedule TO}
Tender offer filing used in acquisitions, buyouts, and going-private transactions. Useful for understanding the terms, financing, and parties involved in a tender offer.
\begin{itemize}
\item Acquisitions
\item Buyouts
\item Going-private transactions
\end{itemize}



\subsection{Securities Offerings}

\subsubsection{Form S-1}
Form S-1 is the registration statement typically used by companies seeking to go public through an initial public offering (IPO). It is useful for understanding a company before its IPO. Typical contents include:
\begin{itemize}
  \item Detailed business description
  \item Risk factors
  \item Use of proceeds
  \item Management team
  \item Industry overview
\end{itemize}

\subsubsection{Form S-3}
Form S-3 is a simplified registration statement used by eligible seasoned issuers to register additional securities offerings. It is commonly used for follow-on offerings and shelf registrations.


\subsection{Ownership and Insider Activity}

\subsubsection{Schedule 13D}
Filed when an investor acquires more than 5\% of a company's shares and intends to influence management or corporate policies. Useful for identifying activist investors, takeover attempts, and significant ownership positions.

\subsubsection{Schedule 13G}
A simplified alternative to Schedule 13D for passive investors who acquire more than 5\% of a company's shares without seeking to influence management or control of the company.

\subsubsection{Form 4}
Reports purchases and sales of company securities by directors, officers, and beneficial owners holding more than 10\% of the company's shares. Useful for tracking insider trading activity.

\subsection{Holdings of Institutional Investors}\label{hii}

\subsubsection{Form 13F}
An aggregated portfolio disclosure by an institutional investment manager. It primarily reports the holdings managed by the filing institutional investment manager, rather than a detailed fund-by-fund portfolio breakdown. The EDGAR form code is \texttt{"13F-HR"} (the holdings report; \texttt{"13F-NT"} is a notice that another manager reports the holdings).

\subsubsection{Form N-PORT}
Individual registered fund portfolio disclosure, providing monthly portfolio reports required for registered open-end investment companies, including most mutual funds and ETFs \footnote{Main exemptions/exceptions include: (1) money market funds, which are primarily regulated under Form N-MFP instead (\S\ref{N-MFP}); (2) exchange-traded products that are not 1940 Act funds; (3) funds relying on master-feeder or umbrella structures; (4) newly formed or liquidating funds may benefit from transitional relief and reduced or modified reporting, respectively; (5) small fund conditional exemptions (limited scope).}. Each filing corresponds to a single registered investment fund. N-PORT filings are typically made public with a delay (generally $\sim$60 days after month-end), and therefore are not real-time.

The public EDGAR form code is \texttt{"NPORT-P"}. N-PORT is highly granular compared to Form 13F:
\begin{itemize}
  \item Individual securities are reported
  \item CUSIPs\footnote{A CUSIP (Committee on Uniform Security Identification Procedures) is a unique nine-character code used to identify North American financial securities, such as stocks, bonds, and mutual funds. Functioning much like a serial number, it uniquely identifies a security and facilitates the accurate tracking of investments, trade processing, and settlement by brokerages, banks, and clearing organizations.} are included
  \item Positions are disclosed at the security level\footnote{Certain holdings may receive confidential treatment in limited, regulator-approved cases.}
  \item Valuation per holding is provided
\end{itemize}

\noindent N-PORT filings may also include portfolio-level classifications and summaries, including,
\begin{itemize}
  \item Equity vs fixed income vs derivatives breakdowns
  \item Sector and asset-type classifications
  \item Country and currency exposure summaries
  \item Liquidity categories
\end{itemize}

\noindent N-PORT filings may further include risk and exposure metrics (where applicable), including,
\begin{itemize}
  \item Portfolio duration (for fixed income)
  \item VaR-style risk measures (where applicable)
  \item Concentration levels
  \item Exposure breakdowns across risk factors
\end{itemize}

\subsubsection{Form N-MFP}\label{N-MFP}
Most money market funds are not required to file N-PORT in the same way as other mutual funds. They are primarily regulated under Form N-MFP instead, which is tailored specifically to money market instruments. The current EDGAR form code is \texttt{"N-MFP2"} (\texttt{"N-MFP3"} from the 2024 amendments).

\subsection{Statement types}\label{sec:edgar-statements}

The periodic reports (10-K, 10-Q) and their foreign equivalents (20-F, 40-F) carry the issuer's financial
statements as \textbf{inline XBRL}: the \textbf{balance sheet}, \textbf{income statement}, \textbf{statement
of comprehensive income}, \textbf{cash-flow statement} and \textbf{statement of changes in equity}. Domestic
filers tag against the \texttt{us-gaap} taxonomy; a foreign private issuer reporting under IFRS tags against
\texttt{ifrs-full}. \texttt{facts(f)} recovers every tagged fact and \texttt{facts(f;\ classify=true)} sorts
each onto its statement (\S\ref{sys:extraction}); from there the same row table feeds
\texttt{select\_statement}, the CSV/DuckDB exports and the validation oracles (\S\ref{sec:validation}). The
8-K and 6-K are event-driven narrative filings rather than statement carriers, so they yield press-release
and exhibit text rather than a tagged statement set.

\section{Credentials}\label{sec:edgar-credentials}\label{sec:ua}

The SEC's fair-access policy requires each request to carry a \texttt{User-Agent} header identifying the
requester by name and contact email; requests without it are rejected with HTTP~403. There is \textbf{no API
key or registration} --- users simply identify themselves honestly. It is set once per session as a single
\texttt{"Name email"} string:

\begin{lstlisting}
julia> using EDGAR
julia> set_user_agent("Your Name name@example.com")
\end{lstlisting}

\noindent If the \texttt{User-Agent} is not set, \texttt{EDGAR.jl} raises an error locally and stops
\emph{before} making any request, ensuring compliance.

\subsection{Persisting the User-Agent}
\texttt{set\_user\_agent()} configures only the \emph{current} process, so a new REPL, script or notebook
starts unconfigured. The resolution order is: (1)~an explicit value from \texttt{set\_user\_agent()};
otherwise (2)~the \texttt{SEC\_USER\_AGENT} environment variable; otherwise (3)~an error. To avoid setting it
every session, define the variable once --- in \texttt{startup.jl} or exported from the shell --- and every
future process reads it:

\begin{lstlisting}
ENV["SEC_USER_AGENT"] = "Your Name name@example.com"
\end{lstlisting}

\noindent The User-Agent is not a secret --- it is just the identity sent to the SEC --- so storing it in a
startup file is safe and recommended. \texttt{EDGAR.jl} also manages persistence automatically:

\begin{lstlisting}
julia> persist_user_agent("Your Name name@example.com")
julia> unpersist_user_agent()   # removes the persisted setting
\end{lstlisting}

\chapter{ESEF \textemdash{} European Union}
\label{sys:esef}

ESEF (the \emph{European Single Electronic Format}) is the EU's mandatory reporting format for the
annual financial reports of issuers on EU-regulated markets. It is the second \texttt{FilingSystem}
in \texttt{EDGAR.jl} after EDGAR, and the one that exercises the portability seam
(\S\ref{sec:architecture}): the XBRL \emph{parsing} is the same jurisdiction-agnostic core used for
SEC filings, while ESEF supplies only its own \emph{fetch}, identity and linkbase-location slice. In
code the system type is \texttt{ESEF}\,\texttt{<:}\,\texttt{FilingSystem}.

\section{Entities covered}\label{sec:esef-entities}

ESEF covers a single class of filer: an \textbf{issuer with securities admitted to trading on an
EU-regulated market}, which must publish its annual financial report in this format. There are no fund or
insider filings here --- the regime is the issuer's annual report only (Table~\ref{tab:esef-entities}).

\begin{tabular}{@{}p{0.26\textwidth}p{0.17\textwidth}p{0.20\textwidth}p{0.25\textwidth}@{}}
\toprule
\textbf{Entity type} & \textbf{Example} & \textbf{Primary form} & \textbf{In \texttt{EDGAR.jl}} \\

\subsection{Regulated-market issuers}
An issuer is identified by its \textbf{LEI} (Legal Entity Identifier, ISO~17442), read from the instance's
context entity identifier rather than a CIK: \texttt{EntityId(:lei,\ "506700GE1G29325QX363")}. Examples
include Citycon Oyj (Finnish) and Signify~N.V.\ (Dutch). The filer's home country and the report's language
(an issuer often files several language variants) travel on the discovery handle.

\section{Forms and statement types}\label{sec:esef-forms}

ESEF mandates a single document --- the \textbf{Annual Financial Report (AFR)} --- so there is one form
group, delivered as a self-contained report package.

\subsection{Annual Financial Report}
An ESEF filing is a \emph{report package}: a single ZIP (\texttt{documentType
https://xbrl.org/report-package/2023}) holding \texttt{META-INF/} (the package manifest + an OASIS
\texttt{catalog.xml}), a \texttt{reports/} directory with the primary report (an inline-XBRL \texttt{.xhtml}
or a classic \texttt{.xbrl} instance), and the issuer's bundled extension taxonomy with its linkbases.
Unlike EDGAR --- where the linkbases are loose sibling files fetched over HTTP from the filing's Archives
directory --- everything needed to parse \emph{and} classify the filing lives inside this one ZIP.

\subsection{Statement types}
The AFR carries the issuer's consolidated \textbf{IFRS} financial statements --- balance sheet, income
statement, statement of comprehensive income, cash-flow statement and statement of changes in equity ---
tagged against \texttt{ifrs-full} plus an issuer extension, not \texttt{us-gaap}. Statement classification
therefore reuses the shared IFRS vocabulary (\S\ref{sec:two-axes}), with no SEC-specific machinery (e.g.\
\texttt{FilingSummary.xml}) involved; \texttt{facts(f; classify=true)} sorts each fact onto its statement
and the same row table feeds \texttt{select\_statement}, the exports and the validation oracles.

\section{Reading and discovering packages}

\paragraph{Reading a report package (offline).} \texttt{fetch\_filing(ESEF(), path)} reads a report
package already on disk into the same \texttt{Filing} type used everywhere else, after which the whole
system-agnostic pipeline --- \texttt{facts}, classification, labels, \texttt{calculations},
\texttt{to\_duckdb}, \texttt{statement\_view} --- applies unchanged:

\begin{lstlisting}
f = fetch_filing(ESEF(), "gleif-2024.zip")   # a report-package ZIP on disk
f.entity                                       # EntityId(:lei, "506700GE1G29325QX363")
rows = facts(f; classify = true, labels = true)
select_statement(rows, "BalanceSheet")         # ifrs-full:Assets, Liabilities, Equity, ...
calculations(f)                                # roll-ups from the bundled calculation linkbase
\end{lstlisting}

The bundled presentation/calculation/label linkbases are resolved straight from the ZIP (the ESEF
method of the per-system linkbase fetcher), so classification and roll-ups work with no network access.

\paragraph{Discovery (finding packages).} There is no single EDGAR-style API for ESEF, so discovery
is modelled as a separate \emph{source} axis (\S\ref{sec:architecture}): a \texttt{FilingSource}
yields system-tagged \texttt{FilingHandle}s, and \texttt{fetch\_filing(handle)} downloads and reads
the package. The first source is \texttt{FilingsXBRLOrg} ---
\href{https://filings.xbrl.org}{filings.xbrl.org}, the XBRL-International aggregator (no API key),
which indexes ESEF and related regimes. \texttt{discover} filters by LEI, country and/or year:

\begin{lstlisting}
hs = discover(FilingsXBRLOrg(); lei = "549300P8N0P6KDGTJ206", year = 2023)  # Citycon Oyj
h  = first(filter(h -> endswith(h.url, "-en.zip"), hs))   # an entity often files several variants
f  = fetch_filing(h)                                       # download + read the report package
facts(f; classify = true, labels = true)
\end{lstlisting}

\noindent A handle is the portable currency between discovery and fetch: it carries the system, the
filer's identity (LEI), the opaque filing reference and the package URL. Because the source axis is
distinct from the system axis, one source can feed several systems (filings.xbrl.org also covers
UKSEF), and per-country Officially Appointed Mechanisms (OAMs) can be added later as further
\texttt{FilingSource}s without touching the parse path.

\paragraph{Current limitations.}
\begin{itemize}
  \item \textbf{Standard \texttt{ifrs-full} labels are not bundled.} A report package ships labels only
    for the issuer's \emph{extension} concepts; the canonical \texttt{ifrs-full} labels live in the
    published IFRS taxonomy, which the package references rather than embeds. So with
    \texttt{labels=true} the extension concepts carry native labels but the standard \texttt{ifrs-full}
    concepts do not (their meaning is fully carried by the concept name regardless). Resolving labels
    from the published standard taxonomy --- the same ``delegate to the standard taxonomy'' mechanism
    Companies House requires --- is planned.
\end{itemize}

\section{Germany}
\label{sec:esef-germany}

German listed groups on EU regulated markets file their consolidated IFRS annual report as ESEF iXBRL,
discoverable like any other ESEF filer (this chapter). But Germany is also the clearest case for the PDF
route (Chapter~\ref{ch:pdf}): the \emph{Bundesanzeiger}'s XBRL is not openly retrievable, and a large
share of German accounts --- single-entity statutory accounts in particular --- are published only as
PDF. The notes below record the German particularities the extractor must handle; they were verified
against real reports during testing.

\subsection{Two accounting flavours: HGB and IFRS}

\begin{itemize}
  \item \textbf{HGB} (\emph{Handelsgesetzbuch}, the German commercial code) --- German GAAP, used for the
    \emph{single-entity} statutory accounts (\emph{Jahresabschluss}). Structure: a two-sided \emph{Bilanz}
    (\emph{Aktiva}\,/\,\emph{Passiva}), the \emph{Gewinn- und Verlustrechnung} (\emph{GuV}), the
    \emph{Anhang} (notes) and \emph{Lagebericht} (management report). Filed at the \emph{Bundesanzeiger};
    typically PDF.
  \item \textbf{IFRS} --- the \emph{consolidated} group accounts (\emph{Konzernabschluss}):
    \emph{Konzernbilanz}, \emph{Konzern-Gewinn- und Verlustrechnung}, etc. For regulated-market issuers
    this is the ESEF-tagged report, reachable as iXBRL via filings.xbrl.org; otherwise it too is often
    only PDF.
\end{itemize}

\noindent A single German company can therefore present \emph{both}: a consolidated IFRS report (possibly
ESEF) and a statutory HGB single-entity account (usually PDF).

\subsection{Statement vocabulary}

\begin{table}[h]
\centering
\caption{German statement vocabulary (what to match in a German report).}
\label{tab:de-vocab}
\small
\begin{tabular}{@{}p{0.46\textwidth}p{0.48\textwidth}@{}}
\toprule
\textbf{German} & \textbf{Meaning} \\
\midrule
\emph{Bilanz} & Balance sheet \\
\emph{Aktiva} / \emph{Passiva} & Assets side / equity-and-liabilities side (HGB, two-sided) \\
\emph{Vermögenswerte} / \emph{Eigenkapital und Schulden} & Assets / equity and liabilities (IFRS) \\
\emph{Gewinn- und Verlustrechnung} (\emph{GuV}) & Income statement \\
\emph{Kapitalflussrechnung} & Cash-flow statement \\
\emph{Anhang} & Notes to the accounts \\
\emph{Lagebericht} & Management report \\

\subsection{Format particularities (for extraction)}

\begin{itemize}
  \item \textbf{Number locale.} The dot is the \emph{thousands} separator and the comma the \emph{decimal}:
    \texttt{1.986.546} means 1{,}986{,}546 and \texttt{197,5} means 197.5. Scale markers: \emph{TEUR} /
    \emph{T€} (thousand euro), \emph{Mio.\ €} / \emph{Mio EUR} (million euro). (Reuse the existing
    decimal-comma logic from the XBRL extractor.)
  \item \textbf{Unlabeled totals.} In IFRS German statements the balance-sheet total row is frequently
    \emph{unlabeled} --- a bare sum line with no ``\emph{Summe}''/``\emph{Bilanzsumme}'' text. Detect it
    structurally (sum of the sections), not by its label.
  \item \textbf{Ambiguous ``Summe Aktiva/Passiva''.} The very same words also label the IFRS-9
    financial-instrument category note (carrying amounts by \emph{AC}\,/\,\emph{FVtPL}\,/\,\emph{FLAC})
    --- which is \emph{not} the balance sheet. Locate the statement by its heading/section, not by a bare
    total label.
  \item \textbf{Two-sided and multi-page.} The \emph{Aktiva} and \emph{Passiva} sides are often on
    separate pages, so a balance sheet may span two pages and must be stitched. The \emph{Bilanzsumme}
    appears equal on both sides --- a built-in cross-foot.
\end{itemize}

\noindent These were confirmed end-to-end from PDF, without OCR: a HGB \emph{Jahresabschluss}
(\emph{Bilanzsumme} 197.754~Mio~€, \emph{Aktiva} = \emph{Passiva}) and an IFRS \emph{Konzernbilanz}
(total 1.986.546~T€, assets = equity \(+\) liabilities) both extracted and cross-footed correctly.

\section{France}
\label{sec:esef-france}

French listed groups on EU regulated markets file their consolidated IFRS annual report as ESEF iXBRL,
usually inside the \emph{Document d'enregistrement universel} (DEU / URD) filed with the \textbf{AMF}
(\emph{Autorité des marchés financiers}). As with Germany, France also has a French-GAAP layer that is
typically PDF-only, so the particularities below matter for the PDF route (Chapter~\ref{ch:pdf}); they were
verified against real filings during testing.

\subsection{Two accounting flavours: PCG and IFRS}

\begin{itemize}
  \item \textbf{French GAAP --- the PCG} (\emph{Plan Comptable Général}) --- the \emph{single-entity}
    statutory accounts (\emph{comptes sociaux} / \emph{comptes annuels}): a two-sided \emph{Bilan}
    (\emph{Actif} / \emph{Passif}), the \emph{Compte de résultat}, and the \emph{Annexe} (notes). Filed
    with the registries (\emph{greffe}); typically PDF.
  \item \textbf{IFRS} --- the \emph{consolidated} group accounts (\emph{comptes consolidés}): \emph{Bilan
    consolidé}, \emph{Compte de résultat consolidé}, \emph{Résultat global}, \emph{Tableau de flux de
    trésorerie}, \emph{Variation des capitaux propres}. For regulated-market issuers this is the
    ESEF-tagged report inside the URD.
\end{itemize}

\subsection{Format particularities (for extraction)}

\begin{itemize}
  \item \textbf{``Bilan'', not ``État de la situation financière''.} French IFRS filers overwhelmingly keep
    the traditional \emph{Bilan consolidé} (both LVMH and TotalEnergies do) rather than the literal IFRS
    title. Match on \emph{bilan}, and keep phrase patterns loose (\emph{situation financière};
    \emph{variation des capitaux propres} \emph{without} an \emph{État de} prefix), because headings insert
    words --- \emph{Bilan} \textbf{consolidé}, \emph{état} \textbf{consolidé} \emph{de la situation
    financière}.
  \item \textbf{Number locale.} The thousands separator is a \textbf{space} (often a non-breaking/thin
    space): \texttt{1 234 567,89} = 1{,}234{,}567.89 --- distinct from Germany's dot. The decimal mark is a
    comma. Amounts are usually \emph{en millions d'euros}.
  \item \textbf{The URD is one big combined document} (300--700 pp) and the consolidated statements are a
    short sub-section. Locate them via the \textbf{PDF outline} (§\ref{sec:pdf-classification}) rather than
    by scanning headings: issuers print a brand band atop each statement page that otherwise masks the real
    title.
\end{itemize}

\noindent Confirmed end-to-end from PDF, without OCR, on two filers --- \textbf{LVMH} and
\textbf{TotalEnergies}: \emph{Bilan consolidé}, \emph{Compte de résultat consolidé}, cash-flow and
\emph{Variation des capitaux propres} all extracted and classified (TotalEnergies via its outline; both
halves --- \emph{Actif} and \emph{Passif} --- of the two-part French \emph{Bilan} tag as the balance sheet).

\chapter{UK filing systems}
\label{sys:uk}

The United Kingdom exposes company financial reports through \emph{two distinct channels}, and
\texttt{EDGAR.jl} reaches both. They are not alternatives bolted together --- they are different
\texttt{FilingSource}s (\S\ref{sec:architecture}) that serve different filer populations and, often,
the same company in different formats. This chapter covers both and gives a worked workflow for each.

\section{Entities covered}
\label{sec:uk-channels}

The UK exposes company reports through two channels, each serving a different filer population
(Table~\ref{tab:uk-entities}): the registrar (every UK company) and the FCA's store of regulated-market
disclosures (listed issuers only).

\begin{enumerate}
  \item[\textbf{(a)}] \textbf{Companies House (CH)} --- the UK \emph{registrar}. \emph{Every} UK
    company must file annual accounts here, so CH spans the whole population (public \emph{and}
    private). A company is identified by its \textbf{registration number}
    (\texttt{EntityId(:companies\_house,\ \ldots)}), and accounts are tagged against UK GAAP
    (FRS~101/102/105, the FRC taxonomy) or IFRS. A CH filing carries \textbf{no issuer extension
    taxonomy}, so labels and classification \emph{delegate} to the published \emph{standard} taxonomy
    for a concept's prefix. Access is the Companies House API (free key), with a keyless
    whole-registrar bulk product as an alternative.

  \item[\textbf{(b)}] \textbf{The National Storage Mechanism (NSM)} --- the FCA's official store of
    \emph{regulated-market} disclosures. It covers only \textbf{listed issuers}, whose
    \textbf{Annual Financial Reports} are filed as \textbf{UKSEF} --- the UK profile of ESEF
    (\S\ref{sys:esef}): inline-XBRL report packages, \texttt{ifrs-full} plus an issuer extension,
    identified by \textbf{LEI}. Because UKSEF \emph{is} ESEF in form, these parse through the shared
    ESEF report-package path unchanged; the NSM supplies only its own discovery and fetch. Access is a
    keyless JSON API.
\end{enumerate}

\subsection{Statement types}
UK accounts are tagged under one of two taxonomy families: \textbf{UK GAAP} --- the FRC's FRS~101/102/105
taxonomy --- or \textbf{IFRS} (\texttt{ifrs-full}). Disclosure scope varies with the standard: a
micro-entity (FRS~105) filing is the most abridged, while FRS~102 and IFRS accounts carry the full balance
sheet and income statement, with cash-flow and changes-in-equity statements where required. A Companies
House filing carries \emph{no issuer extension taxonomy}, so labels and classification \emph{delegate} to
the published \emph{standard} taxonomy for each concept's prefix; a UKSEF report on the NSM instead tags
against \texttt{ifrs-full} plus an issuer extension, exactly as ESEF. When a filing is served as PDF rather
than (i)XBRL (Table~\ref{tab:ch-formats}), no tagged statement set is produced and it belongs to the
PDF/text track.

\section{Finding a company}
\label{sec:uk-company-search}

Both UK workflows start from an identifier --- a registration number for Companies House, an LEI for
the NSM --- that you rarely know by heart. \texttt{company\_search} is the lookup step \emph{before}
discovery: it turns a name (or a set of criteria) into those identifiers. Like \texttt{discover}, it is
a generic verb dispatched on the source, and every source returns the \emph{same} row type, a
\texttt{CompanyHit}:

\begin{lstlisting}
const CompanyHit = @NamedTuple{name::String, id::EntityId, status::String, type::String,
                              incorporated::Union{Date,Nothing}, sic::Vector{String},
                              address::String, country::String}
\end{lstlisting}

\noindent The vector of hits is a Tables.jl row table (drops straight into \texttt{DataFrames}, CSV,
DuckDB), and \texttt{hit.id} is the system-tagged identity --- pass \texttt{hit.id.value} into
\texttt{discover}. Fields a given registry does not publish are left empty.

\paragraph{Companies House --- by name or by criteria.}
\begin{lstlisting}
company_search(CompaniesHouseApi(), "tesco")                 # ranked free-text (name or number)
# Any criterion switches to the advanced search (filters server-side):
company_search(CompaniesHouseApi(), "tesco";
               status = "active", type = "plc", sic = "47110",
               incorporated_from = Date(1900), incorporated_to = Date(1990))
only(company_search(CompaniesHouseApi(), "445790")).id.value # -> "00445790"
\end{lstlisting}

\noindent With only a query it is the registry's ranked search over name and number; supplying any of
\texttt{status}, \texttt{type}, \texttt{sic}, \texttt{incorporated\_from}/\texttt{incorporated\_to},
\texttt{dissolved\_from}/\texttt{dissolved\_to} or \texttt{location} switches to the advanced endpoint,
which filters server-side. Hits populate the full \texttt{CompanyHit} (status, type, incorporation date,
SIC, address).

\paragraph{NSM --- name to LEI.} The NSM is a disclosure store, not a registry, so its search resolves
a name to the issuer's LEI:
\begin{lstlisting}
hit = only(company_search(NSM(), "tesco"))      # id.value = the LEI; registrar fields empty
discover(NSM(); lei = hit.id.value, year = 2025)
\end{lstlisting}

\noindent By default it scopes to the inline-XBRL Annual Financial Reports (the filings that carry an
LEI \emph{and} that the adapter can fetch), deduplicated to one row per issuer; the registrar facets
(\texttt{status}, \texttt{type}, \texttt{incorporated}, \texttt{sic}, \texttt{address}) are therefore
empty. A consequence of that scoping: an issuer that has filed \emph{only} PDF annual reports --- which
includes everything before FY2021 --- has no tagged record to match, so it does not resolve here.

\section{Workflow Use Case Examples}
\label{sec:uk-workflows}

This section gives a worked workflow for each UK channel --- a few lines each --- from identity through
fetch to extraction; more examples will follow.

\subsection{Companies House workflow}
\label{sys:companieshouse}

Identity is the registration number. Set the API key once (or the
\texttt{COMPANIES\_HOUSE\_API\_KEY} environment variable), discover a company's accounts, fetch, and
--- when the filing is XBRL --- run the same system-agnostic pipeline as everywhere else.

\begin{lstlisting}
using EDGAR
set_credentials(CompaniesHouse(); api_key = ENV["COMPANIES_HOUSE_API_KEY"])

# Discover a company's accounts by registration number (newest first).
hs = discover(CompaniesHouseApi(); company_number = "00021497")

# Narrow within a company: a filing-type code and a period-end date range or single year.
hs = discover(CompaniesHouseApi(); company_number = "00445790", type = "AA", from = Date(2020))
hs = discover(CompaniesHouseApi(); company_number = "00445790", type = "AA", year = 2023)

f  = fetch_filing(first(hs))      # a Filing; always inspect f.kind before parsing
f.kind                            # :ixbrl | :xbrl | :pdf  -- not predictable in advance

if f.kind in (:ixbrl, :xbrl)
    rows = facts(f; classify = true, labels = true)   # FRS/IFRS facts (uk-core, ...)
    select_statement(rows, "BalanceSheet")
end

# Keyless alternative: the whole-registrar bulk Accounts Data Product (no API key).
hs = discover(CompaniesHouseBulk(); date = "2026-06-19", company_number = "00021497")
f  = fetch_filing(first(hs))
\end{lstlisting}

\noindent \texttt{discover(CompaniesHouseApi())} filters server-side by \texttt{category} (default
\texttt{"accounts"}) and, within a company, narrows further by \texttt{type} (a filing-type code such
as \texttt{"AA"} for full accounts) and the accounting period end --- either a \texttt{from}/\texttt{to}
range or a single \texttt{year} (the same date filter the NSM offers, \S\ref{sys:nsm}).
Labels and classification delegate to the published FRC \emph{standard} taxonomy (the
filing bundles no extension), so \texttt{labels=true} resolves FRS concept labels with no per-filing
linkbase. A filing whose accounts are PDF returns \texttt{f.kind == :pdf} with the content URL
retained; structured facts are not extracted from it (PDF extraction is a separate track).

\subsection{NSM (UKSEF) workflow}
\label{sys:nsm}

Identity is the LEI. The NSM serves listed issuers' \textbf{Annual Financial Reports} as UKSEF
report packages, which parse through the shared ESEF path. Browse the category vocabulary, discover by
LEI, then fetch and extract:

\begin{lstlisting}
using EDGAR
set_user_agent("Your Name you@example.com")   # for the UKSEF report-package download

nsm_categories("annual")                       # ["ACS" => "Annual Financial Report", ...]
hs = discover(NSM(); lei = "2138002P5RNKC5W2JZ46", year = 2025)   # Tesco PLC
f  = fetch_filing(first(hs))                   # Filing(:ixbrl) -- a UKSEF report package
rows = facts(f; classify = true, labels = true)
select_statement(rows, "IncomeStatement")      # ifrs-full / issuer-extension revenue, ...
\end{lstlisting}

\noindent \texttt{discover(NSM())} accepts a friendly \texttt{category} (resolved against the active
NSM category vocabulary by \texttt{nsm\_categories}) or a category code directly, and narrows the
accounting-reference date by either \texttt{year} (a single calendar year) or an explicit
\texttt{from}/\texttt{to} window of \texttt{Date}s --- the same within-filer date filter Companies
House offers (\S\ref{sys:companieshouse}). Only the tagged UKSEF packages are XBRL-tagged on the NSM;
the other formats (Table~\ref{tab:nsm-formats}) are untagged xHTML or PDF and raise an informative
error today --- they belong to the same PDF/text track noted for Companies House. The very same UKSEF
package is also reachable via \texttt{discover(FilingsXBRLOrg(); lei)} (\S\ref{sys:esef}); the two are
independent sources for one document, and the Arelle oracle (\S\ref{sec:validation}) cross-checks them.

\paragraph{Three document formats.} The NSM tags every document with a \texttt{tag\_esef} state, and
each maps to a distinct format (Table~\ref{tab:nsm-formats}). The format is \emph{not} fixed by the
kind of filing: an Annual Financial Report can appear in all three states --- even for the same issuer
and period (we observed both a tagged package and a PDF for the same Tesco financial year).

\chapter{EDINET \textemdash{} Japan}
\label{sys:edinet}

EDINET is Japan's FSA disclosure system, and the fourth \texttt{FilingSystem}. A filing is a
\textbf{submission ZIP} of inline XBRL plus its bundled taxonomy --- the same shape as a UKSEF/ESEF
report package --- so it parses through the \emph{shared} report-package reader and the
jurisdiction-agnostic XBRL extractor (\S\ref{sys:esef}, \S\ref{sys:extraction}) essentially unchanged;
EDINET supplies only its API source, the ZIP entry layout (the primary instance lives under
\texttt{XBRL/PublicDoc/}), and the new vocabularies below. Identity is the EDINET code
(\texttt{EntityId(:edinet,\ "E\#\#\#\#\#")}).

\emph{Status:} the system, the offline parse, and the classification vocabularies are
\textbf{implemented and verified}; the live API discovery is implemented but awaits a key; the
language-aware labels and CSV oracle are planned (see below).

\paragraph{Formats.} EDINET serves each filing in three forms, flagged per document by the API's
\texttt{pdfFlag} / \texttt{xbrlFlag} / \texttt{csvFlag}: a human-readable \textbf{PDF} (\texttt{type=2},
out of scope for \texttt{facts()}); the \textbf{inline-XBRL submission ZIP} (\texttt{type=1}) --- the bytes
\texttt{facts(f)} parses; and a \textbf{CSV} of the tagged facts (\texttt{type=5}), the regulator's own
parse used as our oracle (\S\ref{sec:edinet-oracle}). EDINET's XBRL is \emph{inline} (iXBRL embedded in
\texttt{.htm} files under \texttt{XBRL/PublicDoc/}) --- in contrast to DART, whose XBRL is \emph{classic}
and which offers no CSV (\S\ref{sys:dart}).

EDINET receives disclosures from three kinds of filer (Table~\ref{tab:edinet-entities}). The securities
issuers --- ordinary corporations --- file the periodic reports that carry the financial statements
\texttt{EDGAR.jl} extracts; funds and the parties to large-shareholding and tender-offer disclosures file
their own document types. A filer is identified by its \textbf{EDINET code}
(\texttt{EntityId(:edinet,\ "E\#\#\#\#\#")}).

\begin{table}[h]
\centering
\small

\subsection{Statement types}

A Japanese filer's accounting basis may be \textbf{IFRS}, \textbf{Japanese GAAP} or (historically)
\textbf{US-GAAP} --- but its EDINET securities report tags the figures in just \emph{two} EDINET concept
namespaces, which is what classification keys on: \texttt{jpigp\_cor} for IFRS, and \texttt{jppfs\_cor} for
everything else (including US-GAAP-basis filers). \texttt{vocab\_jpgaap.jl} supplies both. The SEC
\texttt{us-gaap} namespace does \emph{not} appear in EDINET --- a flavour is read empirically from the
concept prefixes, and on real annual reports we see \texttt{jpigp\_cor} for Toyota Motor (7203, IFRS),
\texttt{jppfs\_cor} for Nintendo (7974, Japanese GAAP) and a megabank like Mitsubishi UFJ (8306), and
--- notably --- \texttt{jppfs\_cor} again for Canon (7751), a historic US-GAAP name whose EDINET report
is nonetheless Japanese-GAAP-tagged (its US-GAAP statements go to the SEC on a 20-F, not to EDINET):

\begin{itemize}
  \item \textbf{Japanese GAAP} --- the \texttt{jppfs\_cor} namespace (Japan Public Financial Statements),
    e.g.\ \texttt{jppfs\_cor:Assets}, \texttt{jppfs\_cor:NetSales}, \texttt{jppfs\_cor:OperatingIncome},
    \texttt{jppfs\_cor:NetCashProvidedByUsedInOperatingActivities}. Unlike Companies House (which binds the
    FRC namespace to \emph{arbitrary} prefixes), EDINET filers use the \textbf{standard \texttt{jppfs\_cor}
    prefix consistently}, so no canonicalisation is needed.
  \item \textbf{IFRS} --- EDINET's own IFRS taxonomy, the \texttt{jpigp\_cor} namespace with
    \texttt{…IFRS}-suffixed local names: \texttt{jpigp\_cor:RevenueIFRS},
    \texttt{jpigp\_cor:AssetsIFRS}, \texttt{jpigp\_cor:OperatingProfitLossIFRS},
    \texttt{jpigp\_cor:ProfitLossBeforeTaxIFRS},
    \texttt{jpigp\_cor:NetCashProvidedByUsedInOperatingActivitiesIFRS}. Crucially, EDINET IFRS filers do
    \emph{not} tag with the bare \texttt{ifrs-full} concepts, so they need their own anchors --- a gap that
    only surfaced when an IFRS filer was tested, and was then filled from the verified concepts.
\end{itemize}

\noindent Both vocabularies are merged into the scored classification registry alongside \texttt{us-gaap},
\texttt{ifrs-full} and the FRC set, and the right one is selected per filing by concept prefix --- exactly
as for the other systems (\S\ref{sys:extraction}). They were \textbf{verified against four real filings}:
J-GAAP --- Kakaku.com, Yahoo Japan and TIS; IFRS --- the official FSA IFRS sample instance. The right one is
selected per filing by concept prefix, after which a filing flows through the same pipeline as every other
system (\S\ref{sec:edinet-workflows}).

\section{Discovery and labels (pending an API key)}

EDINET discovery is \textbf{date-based}: \texttt{discover(EDINETApi();\ date,\ edinet\_code,\ doc\_type)}
lists a day's submissions from the EDINET REST API and returns handles, filtering server-listed results by
EDINET code and document type (e.g.\ \texttt{"120"} = the annual securities report). It is
implemented but \textbf{awaits live verification with a free Subscription-Key} (set via
\texttt{set\_credentials(EDINET();\ api\_key)} or the \texttt{EDINET\_API\_KEY} environment variable). The
remaining pieces also wait on that key or are planned: the full \textbf{form/document-type} catalogue, the
\textbf{language-aware labels} (\texttt{label\_map(f;\ lang)} --- EDINET's label linkbase carries Japanese
\emph{and} English via \texttt{xml:lang}, the forcing case for multilingual labels), and the EDINET
\textbf{CSV fact export} as an independent parser oracle, described next.

\section{Validation: the EDINET CSV oracle}
\label{sec:edinet-oracle}

Every system in this manual proves its numbers against an independent oracle (\S\ref{sec:validation}):
the SEC path cross-checks \texttt{company\_facts}, and ESEF and Companies House cross-check
\href{https://filings.xbrl.org}{filings.xbrl.org}, the Arelle-backed XBRL-International aggregator.
\textbf{Japan has neither} --- \texttt{company\_facts} is SEC-only, and filings.xbrl.org does not carry
EDINET. Without an oracle, ``\texttt{facts(f)} ran and returned numbers'' is not evidence that the numbers
are \emph{right}: a wrong sign, a dropped scale factor, a mis-resolved period or a corrupted nil reads as
a perfectly ordinary value.

The escape is built into the EDINET document API itself, which serves the \emph{same} filing in two forms:

\begin{itemize}[nosep]
  \item \texttt{GET /documents/\{docID\}?type=1} \(\rightarrow\) the submission \textbf{ZIP} (inline XBRL +
    bundled taxonomy) --- the bytes \emph{we} parse with \texttt{facts(f)}.
  \item \texttt{GET /documents/\{docID\}?type=5} \(\rightarrow\) a \textbf{CSV} of the tagged facts ---
    \textbf{the FSA's own parse of that exact same document}.
\end{itemize}

\noindent So the regulator extracts the facts for us, from byte-identical source. The validation
(planned step \textbf{E4.2}) is therefore the strongest kind available: fetch both forms of one filing,
run \texttt{facts(f)} over the ZIP, and assert our values match the CSV's \textbf{row for row}. It is
\emph{same-document} (not a headline cross-check against a different data provider),
\emph{authoritative} (the regulator's own parser, the JP analogue of Arelle), \emph{free}, and
\emph{fact-level}. This is exactly the methodology that caught real extraction bugs on the SEC path ---
the \texttt{\&\#8212;} em-dash entity corrupting every nil fact into the value \texttt{8212}, and the
sign-flip on classic (non-inline) instances --- now turned on Japan. (The weaker checks still apply
alongside it: Yahoo Finance headline totals for Tokyo tickers, e.g.\ Toyota \texttt{7203.T}.) Because
\texttt{type=5} is authenticated, the oracle run waits on the same free Subscription-Key as live
discovery.

\chapter{DART \textemdash{} South Korea}
\label{sys:dart}

DART (and its API, OpenDART) is South Korea's FSS disclosure system, and the \textbf{fifth}
\texttt{FilingSystem}. A filing's financials are served as an XBRL \textbf{package} --- a ZIP of the
classic \texttt{.xbrl} instance plus its bundled linkbases --- so, like ESEF and EDINET, it parses
through the \emph{shared} report-package reader and the jurisdiction-agnostic XBRL extractor
(\S\ref{sys:esef}, \S\ref{sys:extraction}). Korea adopted full IFRS as \textbf{K-IFRS}, so the working
thesis is that DART filings classify against the \emph{existing} \texttt{ifrs-full} vocabulary with
\textbf{no new national GAAP} --- and, verified live, they do (\S\ref{sec:dart-kifrs}). Identity is the
eight-digit OpenDART corporate code (\texttt{EntityId(:corp\_code,\ "00126380")}) and/or the six-digit
KRX stock code (\texttt{:stock\_code}).

\emph{Status:} the system, the offline parse, the live API discovery/fetch, the K-IFRS classification and
the language-aware Korean/English labels are \textbf{implemented and verified live} (against Samsung
Electronics and SK~Hynix); independent validation uses the Yahoo Finance cross-check
(\S\ref{sec:dart-oracle}).

\paragraph{Formats.} DART does \emph{not} mirror EDINET's clean PDF/XBRL/CSV triple (\S\ref{sys:edinet}).
It exposes the financials as \textbf{classic XBRL} --- the \texttt{fnlttXbrl} package is a separate
\texttt{.xbrl} instance plus its linkbases, \emph{not} inline XBRL --- and as a pre-parsed \textbf{JSON}
statement API (\texttt{fnlttSinglAcntAll}, the primary statements only --- the FSS's own parse,
\S\ref{sec:dart-oracle}). There is \textbf{no CSV} endpoint (no analogue of EDINET's \texttt{type=5}); the
disclosure document itself (\texttt{document.xml}) is human-readable DART markup, out of scope for
\texttt{facts()}.

\subsection{Statement types: K-IFRS by reuse}\label{sec:dart-kifrs}

DART is the case the two-axis design (\S\ref{sec:two-axes}) was built for: a new \emph{jurisdiction} that
brings \textbf{no new taxonomy}. Because K-IFRS \emph{is} IFRS, a Korean filer's primary statements are
tagged with bare \texttt{ifrs-full} concepts (\texttt{ifrs-full:Assets}, \texttt{ifrs-full:Revenue},
\texttt{ifrs-full:ProfitLoss}, \texttt{ifrs-full:CashFlowsFromUsedInOperatingActivities}, \ldots), which
the existing \texttt{ifrs-full} vocabulary (shared with ESEF, Companies House and EDINET's IFRS filers)
already classifies. \textbf{No \texttt{vocab\_krgaap.jl} was needed.}

This was confirmed on two real FY2023 annual reports (\texttt{fnlttXbrl} packages): Samsung Electronics
(\texttt{5{,}997} facts) and SK~Hynix (\texttt{6{,}306} facts). In both, roughly \textbf{80\,\% of
concepts are bare \texttt{ifrs-full}} (Samsung \texttt{4{,}735}, SK~Hynix \texttt{5{,}072}); the remainder
are the filer's own \texttt{entity\ldots} extensions ($\sim$11\,\%) and Korea-specific \texttt{dart} /
\texttt{dart-gcd} concepts ($\sim$10\,\%). The balance sheet, income statement and cash-flow statement all
classify through the shared vocabulary, and \texttt{select\_statement} round-trips on both filers (Samsung
BS~1757 / IS~409 / CF~227; SK~Hynix BS~2043 / IS~126 / CF~216); a filing flows through the same pipeline as
every other system (\S\ref{sec:dart-workflows}).

\noindent Even the Korea-specific lines classify without a vocabulary. \textbf{Operating income}
(\krcjk{영업이익}{\emph{yeongeop iik}}) is tagged \texttt{dart:OperatingIncomeLoss} --- a \texttt{dart}-namespace
concept, not \texttt{ifrs-full} --- yet \texttt{facts(f;\ classify=true)} still places it on the income
statement, because the classification engine reads the filing's \emph{presentation-linkbase statement
roles}, not concept anchors alone (\S\ref{sys:extraction}). So a national extension is classified by
\emph{where} it sits in the income-statement role, and no \texttt{vocab\_krgaap.jl} is needed at all ---
verified on Samsung, where \texttt{dart:OperatingIncomeLoss} and numerous other \texttt{dart}/\texttt{entity}
lines (e.g.\ cash-flow proceeds) are correctly bucketed. This is a stronger result than EDINET's, which
needed a \texttt{jpigp\_cor} vocabulary addition (\S\ref{sys:edinet}): for K-IFRS, reuse plus role-based
classification suffices outright.

\section{Discovery and the corp-code resolver}

Unlike EDINET (date-based), OpenDART discovery is \textbf{by company}, because DART publishes a clean
identity index. \texttt{discover(OpenDARTApi();\ corp\_code|stock\_code,\ bgn\_de,\ end\_de)} lists a
company's periodic disclosures from \texttt{list.json} and returns handles, keeping the annual business
report (\krcjk{사업보고서}{\emph{saeop bogoseo}}) and pointing each handle at the \texttt{fnlttXbrl} financial-statement package
(\texttt{reprt\_code\ =\ "11011"}). A free \texttt{crtfc\_key} is required, set via
\texttt{set\_credentials(DART();\ api\_key)} or the \texttt{DART\_API\_KEY} / \texttt{OPENDART\_API\_KEY}
environment variable. (OpenDART authenticates with the key as a \emph{query parameter}, not a header, so
unlike the other keyed systems \texttt{system\_headers(::DART)} is empty and the key is appended to the
URL.)

Every other OpenDART endpoint is keyed by the \texttt{corp\_code}, not the public ticker, so resolution
goes through \texttt{corpCode.xml} --- a ZIP holding one \texttt{CORPCODE.xml} that maps
\texttt{corp\_code\ $\leftrightarrow$\ stock\_code\ $\leftrightarrow$\ name} for \emph{every} registered
Korean entity ($\sim$118{,}000; $\sim$4{,}000 listed). \texttt{dart\_corp\_code("005930")} resolves a
ticker (or a name) to its \texttt{corp\_code}, parsing that index in a single linear pass
(\texttt{0.84\,s} for 118{,}371 rows) and caching it (\S\ref{sec:dart-caching}).

\paragraph{Bilingual labels.} DART's label linkbase is \emph{split per language} ---
\texttt{\ldots\_lab-ko.xml} (Korean) and \texttt{\ldots\_lab-en.xml} (English), each single-language ---
unlike EDINET's one bilingual file. So \texttt{label\_map(f;\ lang)} (and \texttt{facts(f;\ labels=true,\
lang)}) selects the file for the requested language: \texttt{lang="en"} yields English labels,
\texttt{lang="ko"} Korean. On Samsung this gives 1{,}742 labels in each language (e.g.\
\texttt{dart:OperatingIncomeLoss} \(\to\) ``Operating income(loss)'' / ``\krcjk{영업이익(손실)}{yeongeop iik (sonsil)}'').
The \texttt{lang} keyword threads through the shared linkbase fetcher but is consulted only by systems
with per-language label files (just DART today); every other system ignores it, so their behaviour is
unchanged.

\section{Caching: slow endpoints and the per-system policy}\label{sec:dart-caching}

OpenDART's \emph{document} endpoints are \textbf{pathologically slow} --- measured at $\sim$12\,KB/s, so a
single \texttt{fnlttXbrl} filing takes minutes and \texttt{corpCode.xml} (\texttt{3.4\,MB}) clocked
\textbf{293\,s} --- while its metadata \texttt{list.json} answers in $\sim$1\,s. This is the forcing case
for the \textbf{per-system cache policy} (\S\ref{sec:caching}): a single global cache mode is too coarse
when DART is minutes-slow but the SEC and ESEF are fast. \texttt{set\_cache\_policy(DART();\
cache\ =\ :persistent)} makes \emph{only} DART persist its downloads across sessions (each slow file paid
once, ever) while everything else keeps the ephemeral default. It is the recommended setting for any
sustained DART work.

The corp-code index has its own renewal rule, because the
\texttt{corp\_code\ $\leftrightarrow$\ stock\_code} mapping is stable: rather than the global 24\,h
\texttt{cache\_ttl} (which would re-pay the multi-minute download daily), it is rebuilt only when older
than a jurisdiction-specific backstop --- \textbf{30 days} by default, tunable with
\texttt{dart\_index\_ttl!(days)}. As an immediate self-heal for newly-listed companies, a \emph{ticker}
lookup that misses re-downloads the index once and retries; \texttt{dart\_corp\_code(q;\ refresh\ =\
true)} forces a fresh pull on demand.

\section{Validation: independent cross-checks}\label{sec:dart-oracle}

Korea is the hardest jurisdiction to validate independently. filings.xbrl.org does \textbf{not} carry KR,
so there is no Arelle xBRL-JSON oracle (unlike ESEF/UKSEF, \S\ref{sec:validation}), and
\texttt{company\_facts}/AlphaVantage are US-centric. The independent reference that \emph{does} cover Korea
is \textbf{Yahoo Finance}, whose KRX coverage uses the suffixes \texttt{.KS} (KOSPI) and \texttt{.KQ}
(KOSDAQ) --- e.g.\ Samsung \texttt{005930.KS}, SK~Hynix \texttt{000660.KS}. The do-it-yourself oracle
\texttt{src/sources/yahoo\_oracle.jl} compares EDGAR.jl's revenue, net income, assets and equity for the
latest annual report against Yahoo's --- an \emph{independent data pipeline}, the same arms-length check it
applies to every other jurisdiction. One DART subtlety the wiring handles: the consolidated face line is
not left undimensioned but tagged on the \texttt{ConsolidatedAndSeparateFinancialStatementsAxis}
(\texttt{ConsolidatedMember}), so those face facts are normalised to undimensioned for the shared metric
picker.

Yahoo covers only headline totals, so the \textbf{statement of changes in equity} --- a movements-by-equity-component
table --- needs a fact-level, dimension-aware reference. That is the \textbf{local Arelle oracle}
(\texttt{src/sources/arelle\_local\_oracle.jl}, \S\ref{sec:validation}): it runs Arelle itself on the
downloaded \texttt{fnlttXbrl} package and compares \emph{every} fact, keyed by concept~+~period~+~full
dimension set, so the per-component SCE cells are checked individually. On Samsung FY2023 it confirms
\textbf{5997/5997} of EDGAR.jl's facts against Arelle --- all five statements, the SCE included
(159/159) --- comparing values \emph{raw} (Arelle reports the as-stored value; EDGAR.jl's classified value
flips sign for \texttt{negatedLabel}/cash-outflow concepts).

OpenDART additionally re-serves each filing's parsed accounts as \texttt{fnlttSinglAcntAll.json} (the FSS's
own parse). It is a handy sanity peek --- \texttt{account\_id} values such as \texttt{ifrs-full\_Assets} map
straight onto our concepts --- but because it comes from the \emph{same} disclosure system as the filing it
is not an independent reference, so EDGAR.jl ships no comparison harness for it.

\section{Credentials}\label{sec:dart-credentials}

OpenDART requires a \emph{free} \texttt{crtfc\_key} (register on the OpenDART portal). Set it per session, or
from the environment:

\begin{lstlisting}
set_credentials(DART(); api_key = ENV["DART_API_KEY"])
\end{lstlisting}

\noindent The same key authenticates discovery, the \texttt{fnlttXbrl} package download and the
\texttt{corpCode.xml} resolver.

\chapter{Additional Data Sources}
\label{sec:validation}

How do you know the numbers \texttt{EDGAR.jl} extracts are right? You can check them against
independent references --- ``trust, but verify.'' \texttt{EDGAR.jl} ships four \emph{do-it-yourself}
data sources under \texttt{src/sources/}, each an independent reference you compare the extraction
against. They are deliberately \textbf{not part of the \texttt{EDGAR} module} (not \texttt{include}d by
\texttt{src/EDGAR.jl}), so they add \textbf{no dependencies} to the package and never touch the working
code; you load one on demand when you want reassurance. A stray \texttt{.jl} file under \texttt{src/}
is ignored by the package loader.

\begin{table}[h]
\centering
\caption{The four additional data sources (validation oracles).}
\label{tab:oracles}
\small
\begin{tabular}{@{}p{0.30\textwidth}p{0.26\textwidth}p{0.18\textwidth}p{0.12\textwidth}@{}}
\toprule
\textbf{Reference} & \textbf{Kind} & \textbf{Coverage} & \textbf{Extra deps} \\
\midrule
\textbf{Yahoo Finance} (via \texttt{YFinance.jl}) & \emph{data} check --- independent pipeline; headline totals within 1\% & global (100+ countries) & \texttt{YFinance} \\
\textbf{AlphaVantage} (official REST API) & \emph{data} check --- independent pipeline; headline totals within 1\% & US-strong (SEC filers) & none \\
filings.xbrl.org \textbf{xBRL-JSON}, produced by \textbf{Arelle} (the reference XBRL processor) & \emph{parser} check --- same document, independent parser; fact-level parity & ESEF + UKSEF (EU, UK) & none \\
\textbf{Arelle run locally} (the reference XBRL processor, as a subprocess) & \emph{parser} check --- same document, fact-level \textbf{incl.\ dimensions} (covers the SCE) & \textbf{any} XBRL package (incl.\ KR, JP) & Arelle CLI \\
\bottomrule
\end{tabular}
\end{table}

\noindent They answer two different questions. A \textbf{data} oracle (\textbf{Yahoo Finance},
\textbf{AlphaVantage}) confirms the \emph{numbers match the outside world}: it compares the headline
totals (Assets, Equity, Revenue, Net income, operating cash flow) against an entirely separate data
pipeline, across all three statements. A \textbf{parser} oracle (\textbf{Arelle}) confirms we
\emph{read the filing right}: it compares the extracted facts against the \emph{same filing} as parsed by
the reference XBRL processor. There are two: \texttt{arelle\_esef\_oracle.jl} fetches Arelle's
\emph{already-published} xBRL-JSON from filings.xbrl.org (no dependency, but limited to the ESEF/UKSEF
filings the aggregator hosts and to consolidated facts), while \texttt{arelle\_local\_oracle.jl} \emph{runs}
Arelle locally on the filing itself (needs the Arelle CLI, but then validates \emph{any} filing --- SEC,
ESEF/UKSEF, Korea/DART, Japan --- and \emph{every} fact, dimensions included, so it covers the statement of
changes in equity). It accepts whatever shape a filing comes in:

\begin{itemize}[nosep]
  \item a \textbf{bare inline-XBRL/XBRL instance} --- e.g.\ a SEC filing, whose \texttt{f.url} is the inline
    \texttt{.htm} (not a ZIP); Arelle is pointed at the URL (or a local file) and fetches the DTS itself;
  \item a formal \textbf{report package} (ESEF/UKSEF, carrying \texttt{META-INF/taxonomyPackage.xml}) ---
    handed to Arelle \emph{as a package} so its catalog remaps the standard taxonomy;
  \item a \textbf{loose package} (DART \texttt{fnlttXbrl}, an EDINET submission) --- extracted, with Arelle
    pointed at the instance.
\end{itemize}

\noindent Both oracles compare values \emph{raw} (the as-stored value; the classified value flips sign for
\texttt{negatedLabel}/cash-outflow concepts). The local oracle is verified at \textbf{100\%} on the five
financial statements (balance sheet, income statement, comprehensive income, cash flow and changes in
equity) across SEC (Apple 10-K), ESEF (Citycon, 312/312), UKSEF (Kainos) and DART (Samsung, 5997/5997);
the few unconfirmed facts are note-level non-financial disclosures (counts, percentages). A parser oracle
cannot catch a filer \emph{mis-tagging} a value (everyone reads the same wrong tag); a data oracle can, but
only approximately, since the data providers normalize.

\medskip\noindent This is the same kind of check the package already applies on the SEC side: the
extracted values are validated against the SEC's \texttt{companyfacts} API (the SEC's own parse of the
same filing). Each filing system has an independent reference of this sort --- which is what lets us
trust the one jurisdiction-agnostic parser across systems where no such API exists
(\S\ref{sec:architecture}). Each oracle's \texttt{validate} returns a row table --- one row per fact
(or per headline metric) with the \texttt{EDGAR} value, the reference value, the relative difference
and a \texttt{match} flag --- so you can \texttt{filter} to mismatches or render it with
\texttt{PrettyTables}. A \texttt{User-Agent} must be set first (\S\ref{sec:ua}); the scripts fall
back to the \texttt{EDGAR\_UA} environment variable.

\section{Yahoo Finance}

A \emph{data} oracle with the broadest reach: Yahoo Finance covers 100+ countries, so it cross-checks
SEC and ESEF filers alike. It compares the headline totals against Yahoo's standardized fundamentals
within a 1\% tolerance (Yahoo rounds). It needs \texttt{YFinance.jl} in the active environment --- a
dependency that is \emph{earned}, because Yahoo has no official API: its endpoints are undocumented and
cookie/crumb-gated, and \texttt{YFinance.jl} encapsulates that fragile access.

\paragraph{Validating the extraction.} Extract a filer with \texttt{EDGAR}, then cross-check its
headline totals against Yahoo:

\begin{lstlisting}
using YFinance
include(joinpath(pkgdir(EDGAR), "src", "sources", "yahoo_oracle.jl"))
using .YahooOracle

# 1. EDGAR side -- Apple's latest 10-K, classified (the figures under test).
f = fetch_filing("320193", first(filings_by_cik("320193"; forms = "10-K")).accession)
select_statement(facts(f; classify = true), "BalanceSheet")     # eyeball EDGAR's numbers

# 2. Cross-check the five headline totals against Yahoo (an independent pipeline).
v = YahooOracle.validate(:sec, "320193", "AAPL")   # CIK or LEI + the Yahoo ticker
filter(r -> !r.match && r.yahoo !== nothing, v)    # empty => all agree within 1%
YahooOracle.report()                               # or the built-in multi-firm panel
\end{lstlisting}

\paragraph{Why a \texttt{ticker}?} A \texttt{Filing} knows the filer's \texttt{EntityId} (CIK or LEI),
not its exchange symbol, so the data oracles take the ticker explicitly (\texttt{"AAPL"},
\texttt{"CTY1S.HE"}). The same applies to AlphaVantage below.

\section{AlphaVantage}

A second \emph{data} oracle, strongest for US (SEC) filers. Unlike Yahoo it needs \textbf{no extra
dependency}: AlphaVantage is an official, documented REST API (one keyed GET returns clean JSON), so
the oracle uses \texttt{EDGAR}'s own cached fetcher directly. That caching matters --- the free key
allows only \(\sim\)25 calls/day, so the on-disk response cache makes re-runs free, and a fresh run is
paced under the \(\sim\)5/minute limit (a burst of four network calls per minute; cached calls never
block). Set the free key once (it falls back to the \texttt{ALPHA\_VANTAGE\_API\_KEY} environment
variable):

\begin{lstlisting}[style=term]
# https://www.alphavantage.co/support/#api-key
% export ALPHA_VANTAGE_API_KEY="your-key"
% julia --project=. src/sources/alphavantage_oracle.jl   # the built-in US panel
\end{lstlisting}

\paragraph{Validating the extraction.} Extract a US filer with \texttt{EDGAR}, then cross-check against
AlphaVantage's fundamentals:

\begin{lstlisting}
include(joinpath(pkgdir(EDGAR), "src", "sources", "alphavantage_oracle.jl"))
using .AlphaVantageOracle

# 1. EDGAR side -- Microsoft's latest 10-K, classified.
f = fetch_filing("789019", first(filings_by_cik("789019"; forms = "10-K")).accession)
select_statement(facts(f; classify = true), "IncomeStatement")

# 2. Cross-check against AlphaVantage (cached; a fresh run is paced under the free tier).
v = AlphaVantageOracle.validate(:sec, "789019", "MSFT")   # CIK + the AlphaVantage symbol
filter(r -> !r.match && r.alphavantage !== nothing, v)    # real disagreements only
AlphaVantageOracle.report()                               # or the built-in US panel
\end{lstlisting}

\noindent On the default panel the balance-sheet totals match the extraction to \texttt{0.000\%}.
A metric AlphaVantage did not return (e.g. a throttled call) has \texttt{alphavantage === nothing} and
is \emph{not} counted as a mismatch --- hence the \texttt{!== nothing} filter above.
Throttle responses (which AlphaVantage returns with HTTP~200) are purged from the cache so they cannot
poison a later run.

\section{Arelle}

\textbf{Arelle} is the reference, open-source XBRL processor --- an independent implementation of the
standard. \texttt{EDGAR.jl} validates against it two ways, both \emph{parser} oracles (same document,
fact-level): the \textbf{local} oracle runs Arelle itself on the filing and covers \emph{every}
\texttt{FilingSystem} and \emph{every} fact; the \textbf{published-JSON} oracle reuses Arelle's output from
filings.xbrl.org with no extra dependency, for the ESEF/UKSEF filings that aggregator hosts.

\subsection{Local Arelle --- the universal oracle}

\texttt{arelle\_local\_oracle.jl} runs the Arelle CLI (\texttt{arelleCmdLine}) on the downloaded filing and
compares EDGAR.jl's value for \emph{every} fact --- keyed by concept + period + full \emph{dimension} set
--- against Arelle's. Because it keys on dimensions, it validates the dimensional statements the headline
data checks cannot, in particular the \textbf{statement of changes in equity}. It needs the Arelle CLI
installed (located via the \texttt{ARELLE\_CMD} env var, \texttt{PATH}, or the macOS app), and accepts
whatever shape a filing arrives in:

\begin{itemize}[nosep]
  \item a \textbf{bare inline-XBRL/XBRL instance} (SEC --- \texttt{f.url} is the inline \texttt{.htm}, not a
    ZIP); Arelle is pointed at the URL/file and fetches the DTS itself;
  \item a formal \textbf{report package} (ESEF/UKSEF, with \texttt{META-INF/taxonomyPackage.xml}) --- handed
    to Arelle \emph{as a package} so its catalog remaps the standard taxonomy;
  \item a \textbf{loose package} (DART \texttt{fnlttXbrl}, an EDINET submission) --- extracted, with Arelle
    pointed at the instance.
\end{itemize}

\noindent Values are compared \textbf{raw} (as stored): EDGAR.jl's classified value flips sign for
\texttt{negatedLabel}/cash-outflow concepts, so the classification is used only to \emph{label} each row by
statement, never to compare. The oracle is verified at \textbf{100\,\% on the financial statements ---
including the changes-in-equity statement --- across every \texttt{FilingSystem}}: SEC (Apple 10-K), ESEF
(Citycon, 312/312), UKSEF (Kainos), DART (Samsung, 5997/5997) and EDINET (Toyota 1378/1378; Nintendo, MUFG
and Canon also 100\,\%). The handful of unconfirmed facts are note-level non-financial disclosures (counts,
percentages).

\begin{lstlisting}
include(joinpath(pkgdir(EDGAR), "src", "sources", "arelle_local_oracle.jl"))
using .ArelleLocalOracle

# Any filing, any system: materialise it, run Arelle, compare every fact (incl. the SCE).
f = fetch_filing(EDINET(), "Toyota-annual.zip")
ArelleLocalOracle.report(ArelleLocalOracle.validate(f))      # per-statement parity
filter(r -> !r.match, ArelleLocalOracle.validate(f))         # any discrepancies

# DART convenience -- discover + validate in one call:
set_credentials(DART(); api_key = ENV["DART_API_KEY"])
ArelleLocalOracle.report_dart("005930"; year = 2023)         # Samsung -- 5997/5997, incl. SCE
\end{lstlisting}

\subsection{Published xBRL-JSON --- ESEF/UKSEF, no dependency}

\texttt{arelle\_esef\_oracle.jl} skips the local install: it fetches the \emph{same filing's} xBRL-JSON as
\textbf{already published} by \href{https://filings.xbrl.org}{filings.xbrl.org} (produced by Arelle), using
just the HTTP+JSON \texttt{EDGAR} already has. So it adds no dependency, but is limited to the ESEF + UKSEF
filings the aggregator hosts and to consolidated (undimensioned) facts. It mirrors
\href{https://github.com/trr266/ESEF.jl}{\texttt{ESEF.jl}}'s \texttt{pluck\_xbrl\_json} (MIT, TRR~266) ---
credit there.

\begin{lstlisting}[style=term]
# the built-in firm panel (exits non-zero if parity drops below 95%):
% julia --project=. src/sources/arelle_esef_oracle.jl
\end{lstlisting}

\paragraph{Validating the extraction.} Discover and extract an ESEF/UKSEF filer with \texttt{EDGAR}, then
check every consolidated fact against the same filing's xBRL-JSON:

\begin{lstlisting}
include(joinpath(pkgdir(EDGAR), "src", "sources", "arelle_esef_oracle.jl"))
using .ArelleEsefOracle
filter(r -> !r.match, ArelleEsefOracle.validate("549300P8N0P6KDGTJ206"; year = 2023))  # discrepancies
ArelleEsefOracle.statements("549300P8N0P6KDGTJ206")    # parity per BS / IS / CF (e.g. 100%)
\end{lstlisting}

\noindent \texttt{ArelleEsefOracle.statements(lei)} reports parity \emph{per statement} --- one row
\texttt{(statement, matched, total)} for \texttt{BalanceSheet}, \texttt{IncomeStatement} and
\texttt{CashFlow} --- near-exact on the default panel (\textbf{100\,\% fact parity}).



\chapter{Related Work and Comparison}
\label{sec:related-work}

EDGAR.jl enters a mature ecosystem of EDGAR/XBRL tooling, mostly in Python and R. It is
worth being explicit about where it follows the field, where it differs, and what it does
not (yet) do.

\paragraph{The landscape.} In Python, \href{https://github.com/dgunning/edgartools}{\texttt{edgartools}}
is the modern leader --- it turns filings into typed objects and is especially strong on XBRL
statements, with two ideas we admire: \emph{concept standardization} (mapping each issuer's tag
to a common concept for cross-company comparison) and \emph{statement stitching} (assembling a
multi-period statement across filings). It is, however, in-memory --- it exports to
\texttt{DataFrame}s rather than persisting a warehouse. \href{https://arelle.org/}{Arelle} is the
reference open-source XBRL engine --- the SEC's own EDGAR Renderer is built on it --- and its
\texttt{xbrlDB} plug-in persists facts using the canonical \emph{XBRL-US Public Database} schema.
Tools such as \texttt{sec-edgar-downloader} and \texttt{sec-downloader} fetch raw filings and
leave parsing to you. In R, \texttt{finstr} (on top of the \texttt{XBRL} package) organises
instances into income statements, balance sheets and cash-flow statements. Julia, by contrast,
has had no established EDGAR/XBRL library.

\begin{table}[h]
\centering
\caption{EDGAR.jl among representative EDGAR/XBRL tools.}
\label{tab:related-work}
\small
\begin{tabular}{@{}p{0.16\textwidth}p{0.06\textwidth}p{0.27\textwidth}p{0.15\textwidth}p{0.10\textwidth}p{0.09\textwidth}@{}}
\toprule
\textbf{Tool} & \textbf{Lang} & \textbf{Focus} & \textbf{Persistent warehouse} & \textbf{Concept std.} & \textbf{Picker / prov.} \\
\midrule

\bottomrule
\end{tabular}
\end{table}

\paragraph{What EDGAR.jl does differently.} Three things set it apart. \emph{(1)~An interactive
picker with provenance:} you select a region in the rendered filing, and every extracted fact
carries a \texttt{source\_selector} back to the exact DOM node --- a bridge between document
review, iXBRL semantics and relational analytics that the other tools, which extract purely
programmatically, do not offer. \emph{(2)~An embedded DuckDB warehouse:} zero-server and
single-file, where Arelle persists only to heavy databases and edgartools does not persist at
all --- and facts from any source share one table under a semantic key
(\S\ref{sec:export-layers}). \emph{(3)~A four-layer export} from a single selection --- lossless
iXBRL, Markdown, Facts JSON and DuckDB --- with provenance threaded throughout. And it is
Julia/Tables.jl-native, filling a gap in that ecosystem.

\paragraph{Authoritative enrichment.} A second distinction is \emph{where} EDGAR.jl's enrichment
comes from: a fact's statement is read from the filing's own presentation linkbase
(\texttt{statement\_map}, \S\ref{sec:export-layers}) and its roll-up arithmetic from the
calculation linkbase (\texttt{calculations}), rather than inferred --- and concept standardization
is pluggable (\texttt{set\_standardizer}), defaulting to \emph{none} and offering the bundled,
attributed edgartools mapping opt-in, instead of baking one opinionated mapping in.

\paragraph{What it does not (yet) do.} In fairness, the established tools still lead in breadth.
edgartools covers many more form types (Form 3/4/5, 13F, ADV, \dots) and now ships IFRS mappings,
while Arelle implements the full XBRL specification --- formula, dimensional validation, table
linkbases --- that EDGAR.jl does not. EDGAR.jl focuses on us-gaap financial-statement facts, and
its standardization is the bundled edgartools concept mapping rather than that project's newer,
data-driven one. The gaps an earlier draft named --- concept standardization, statement
classification, and the calculation linkbase --- are now closed
(\texttt{set\_standardizer(:edgartools)}, \texttt{statement\_map}, \texttt{calculations}).

\paragraph{Validation from the reference schema.} Reassuringly, the design we arrived at matches
the XBRL-US reference: it hashes each fact by its context so identical contexts collapse (our
semantic \texttt{fact\_key}), and assigns a fiscal year and period to every fact (our
\texttt{fy}/\texttt{fp}/\texttt{frame}). Where we diverge is deliberate --- the reference
normalises context, unit and dimension into separate tables for transactional Postgres, whereas
EDGAR.jl keeps a \emph{denormalised} wide facts table, which is what an analytical, columnar
store like DuckDB prefers.

\chapter{Glossary}
\label{sec:glossary}

SEC filings and their structured data come with their own vocabulary.
The terms that matter here:

\begin{description}[leftmargin=1.4em,style=nextline,itemsep=2pt]
  \item[CIK] \emph{Central Index Key}, the SEC's unique ID for a filer,
    zero-padded to 10 digits (Apple $\to$ \texttt{0000320193}). Functions accept it
    as an integer or a string, with or without leading zeros (\texttt{320193}
    $\equiv$ \texttt{0000320193}). Look one up from a ticker or company name with
    \texttt{cik}.
  \item[Filing] a document submitted to the SEC, identified by an
    \textbf{accession number} and a \textbf{form type} (\texttt{10-K} annual
    report, \texttt{10-Q} quarterly, \texttt{8-K} current report, \dots). Get a filer's filings with \texttt{filings\_by\_cik}.
  \item[XBRL] \emph{eXtensible Business Reporting Language}, the machine-readable format companies tag their financial statements in; it is what makes the numbers queryable rather than locked inside a document. A pure XBRL filing is an XML document whose primary purpose is to represent structured facts,
  \begin{lstlisting}
<us-gaap:Assets contextRef="CurrentYear" unitRef="USD">
    1000000
</us-gaap:Assets>
\end{lstlisting}
A browser won't render this as a nice financial statement. It's intended for software.
\item[iXBRL] \emph{Inline-XBRL}: those same tags embedded directly inside the filing's human-readable HTML, so one document is both readable and
machine-parseable. The SEC has required it for financial statements since
around 2019. An iXBRL filing is an HTML document that looks like a normal report,
\begin{lstlisting}
<p>
Total assets were
<ix:nonFraction
    name="us-gaap:Assets"
    contextRef="CurrentYear"
    unitRef="USD">
    1000000
</ix:nonFraction>.
</p>
\end{lstlisting}
Historically, iXBRL was defined on top of XHTML (XML-compliant HTML), although modern tools often treat it as HTML with XML namespaces.
  \item[Fact] a single reported number: one \emph{concept}, for one
    \emph{period}, in one \emph{unit} (e.g.\ ``net income for FY2023 was
    96{,}995{,}000{,}000 USD''). \texttt{company\_facts} returns every fact a
    company has reported.
  \item[Concept] the \emph{name} of a reported line item, drawn from a taxonomy
    (e.g.\ \texttt{NetIncomeLoss}, \texttt{Assets}, \texttt{Revenues}) --- ``what is
    being measured''. \texttt{company\_concept} returns one concept over time.
  \item[Taxonomy] a dictionary that defines concepts. The big one is
    \textbf{\texttt{us-gaap}} (US accounting standards); \textbf{\texttt{dei}}
    (\emph{Document and Entity Information}) holds metadata about the filing
    itself; \textbf{\texttt{srt}} holds shared elements; \textbf{\texttt{ifrs-full}}
    is for filers reporting under IFRS; and each company has its own
    \textbf{extension} namespace (e.g.\ \texttt{aapl} for Apple-specific concepts).
  \item[Frame] a cross-section: one concept, one unit, one period, across
    \emph{every} filer that reported it. \texttt{xbrl\_frames} returns a frame.
  \item[Unit] the unit of measure of a fact: \texttt{USD}, \texttt{shares},
    \texttt{USD/shares} (per-share), \texttt{pure} (a ratio), \dots
  \item[Period] the time a fact covers, and how it is written. \textbf{Frames}
    use \emph{calendar} periods: \texttt{CY} + year, as in \texttt{CY2022} (a full
    calendar year), \texttt{CY2022Q4} (a quarter), or \texttt{CY2022Q4I} (a single
    instant --- note the trailing \texttt{I}). An \textbf{instant} is a point in
    time (balance-sheet items such as Assets, at quarter-end); a
    \textbf{duration} is a span (income-statement items such as Revenue). By
    contrast, \textbf{\texttt{FY}} in a company's own facts is its \emph{fiscal}
    year, which need not match the calendar (Apple's \texttt{FY2023} ended in
    September 2023).
\end{description}
